# Stale resource namespace cleanup

Gludd stores checkout-scoped scratch state below a `gludd-resources` root. The
`clean-stale-resource-namespaces` target inventories those directories and can
reclaim only namespaces that are old enough and proven inactive. Inventory is
the default; deletion is an explicit second mode.

## Safety and ZDD contract

The cleaner treats a namespace and its optional `-toolchain` directory as one
ownership unit. It protects the invoking checkout, every Git worktree, and all
worktrees in the active-workstream registry. It then requires all of these
conditions before deletion:

- the root is an exact, owned, non-symlink directory named `gludd-resources`;
- the candidate is a canonical direct child with a 12-hex checkout digest;
- every descendant is owned and readable; ordinary symlinks are treated only as
  entries, while namespace roots, namespace candidates and marker-looking links
  remain refused; regular hard links and multiply linked symlinks are refused;
- the newest descendant is older than the bounded grace period;
- kernel lock inspection proves that no lock is held;
- every PID marker is dead or has a start identity proving PID reuse; and
- a second inventory has the same root, directory inodes, and tree digests.

Missing process census data, corrupt registries, live owners, ambiguous PID
records, changed paths, excessive inventory size, and inspection errors all
preserve data. Apply mode emits progress while recursive deletion is active and
appends one fsynced JSON receipt per removed path outside the cleanup root.

These rules preserve zero-downtime development: cleanup never signals a
process, removes a registered/current namespace, or interrupts an active gate.
It only removes isolated scratch state after activity has been disproved twice.

## Operator workflow

Run a validate-only inventory first:

```console
make clean-stale-resource-namespaces STALE_RESOURCE_NAMESPACE_ROOT=$HOME/tmp/gludd-resources STALE_RESOURCE_NAMESPACE_PROJECT_ROOT=. STALE_RESOURCE_NAMESPACE_REGISTRY= STALE_RESOURCE_NAMESPACE_RECEIPT=$HOME/tmp/gludd-resources.cleanup-receipts.jsonl STALE_RESOURCE_NAMESPACE_GRACE_SECONDS=86400 STALE_RESOURCE_NAMESPACE_MAX_CANDIDATES=1000 STALE_RESOURCE_NAMESPACE_MAX_ENTRIES=100000 STALE_RESOURCE_NAMESPACE_HEARTBEAT_SECONDS=5 STALE_RESOURCE_NAMESPACE_VALIDATE_ONLY=1
```

After reviewing every `reclaim` decision, repeat the exact inputs with
`STALE_RESOURCE_NAMESPACE_VALIDATE_ONLY=0`. Apply mode re-runs ownership and
identity checks before each deletion. A nonzero result means a race or unsafe
observation was preserved and should be investigated, not manually bypassed.

Inventory JSON includes `blocking_marker`: the exact first marker path that
caused an owner or lease refusal, or `null` when no blocking marker was reported.
The field is additive; `action`, `reason`, paired ownership, and every existing
age, process, registry, lease, link, identity, and inventory-bound check are
unchanged. A protected namespace can have `blocking_marker: null` because it is
preserved before scanning; `null` is not proof of inactivity.

The path is captured at the existing rejection point without another traversal,
subprocess, or allocation of a test environment. JSON safely escapes unusual
path characters, including newlines. Marker contents, owner payloads, and other
environment data are not added to the report. Validate-only mode still deletes
nothing and writes no cleanup receipts.

An empty `.lock` file is not itself an ownership record: the existing kernel
lease inspection must also show that the lock is available. Another ambiguous
marker still preserves the entire namespace/toolchain pair. Use the reported
path to investigate its origin and owner; do not assume a marker-looking
installed file is harmless, remove the marker, rename the environment into
another cleanup namespace, or substitute an unguarded directory-clear command.

## Installed artifacts versus runtime owner records

The real retired release toolchain first refused `virtualenv/util/lock.py`,
then generated `_lease.pyc`, and then `ansiblelint/rules/no_same_owner.md`.
The filename matcher remains unchanged. A parsed owner record, held or
unavailable kernel lock, or unknown payload keeps its original refusal.
An installed module requires a unique distribution RECORD entry whose SHA-256
and byte size match, plus actual module syntax; a suffix alone proves nothing.
The owner uses stdlib distribution metadata rather than another package scanner.
[PEP 376](https://peps.python.org/pep-0376/) defines installed-file records.

Generated bytecode additionally needs the current interpreter's canonical cache
path, magic number, flags, and source freshness fields, independently verified
source, and a matching compiler-produced payload. The cache is not deserialized
and the source is not executed. A valid [PEP 552 header](https://peps.python.org/pep-0552/)
alone is not payload proof. Foreign compilers, filename drift, modified source,
missing/duplicate records, and opaque payloads remain refused.

`STALE_RESOURCE_NAMESPACE_PYTHON` optionally selects an existing trusted runtime
for the normal owner. Its default preserves the system interpreter; literal
environment transport avoids Make-function evaluation. Use a protected current
toolchain matching the cache version, never the candidate being reclaimed.
This selection installs nothing and does not replace global or serving Python.
All age, link, process-census, lease, registry and revalidation rules still apply;
successful artifact classification alone is not permission to delete a tree.

Packaged Markdown also needs exact RECORD bytes and a heading parsed by the
already-locked MarkdownIt implementation. A `.md` suffix, opaque owner text,
modified bytes or an unavailable parser is insufficient. Python 3.14's borrowed
arguments can change marshal's reference flag; retaining compiler ownership
reproduces the standard writer without normalizing cache bytes or accepting
another serialization. Historical inventory reached the blanket descendant-symlink refusal;
that retained failure remains valid for its original source, and no recovered
capacity is inferred from it.

## Long-lived operator reports considered

- A [GitHub Actions runner report](https://github.com/actions/runner/issues/4357)
  shows cleanup from an exiting worker deleting the next worker's live shared
  temp files. That failure motivates per-checkout namespaces, paired ownership,
  and protection of every current worktree before considering age.
- An [OpenClaw cleanup report](https://github.com/openclaw/openclaw/issues/165035)
  demonstrates live files being unlinked when process census failed. Gludd
  therefore treats an unavailable census as a global cleanup refusal.
- A [Codex sandbox report](https://github.com/openai/codex/issues/31599) describes
  stale owner markers after abrupt termination and calls out inode-replacement
  races. Gludd records device/inode/tree identities and revalidates them at
  apply time.
- A [Hermes gateway report](https://github.com/NousResearch/hermes-agent/issues/13655)
  documents both stale PID records and PID reuse. Gludd compares PID start
  identity and preserves live PIDs when the marker lacks enough identity data.
- The older [systemd tmpfiles hard-link discussion](https://github.com/systemd/systemd/issues/7736)
  documents recursive cleanup hazards beyond symlinks. Gludd refuses linked
  regular files instead of changing or removing them.
- A [uv shared-directory lock report from 2024-10-09](https://github.com/astral-sh/uv/issues/8032)
  describes lock ownership conflicting with the directory's users. This supports
  reporting the precise blocking path rather than inferring ownership from a
  generic `.lock` filename or an empty record.
- A [uv operator report from 2026-05-13](https://github.com/astral-sh/uv/issues/19395)
  describes data loss after `--clear` targeted a project directory. The
  [uv CLI reference](https://docs.astral.sh/uv/reference/cli/#uv-venv) describes
  that option as clearing a target before creating an environment, not as a
  Gludd ownership-aware retirement mechanism. It is not a cleanup bypass here.

The reports span several cleanup implementations and years, so the feature
encodes their recurring failure modes as tests rather than relying on operator
judgment during disk pressure.


## Ordinary interior links and descriptor-bound inspection (M16)

The 2026-10-18 user clarification permits unlinking ordinary symlink entries
without following their targets. The earlier blanket refusal at immutable
6ade745 preserved retired toolchains even when their interior links were normal
interpreter links. That inventory did not report the actual first link path;
it establishes the blanket refusal, not target danger or reclaimable capacity.

The existing scanner now obtains names through directory descriptors and uses
no-follow metadata and O_DIRECTORY/O_NOFOLLOW opens for every traversed
component. Ordinary links contribute their own uid, inode, link count,
timestamps, byte size and readlink text to the fingerprint. Their target
existence, ownership, age and bytes are irrelevant. Replacing a link, changing
the candidate directory metadata, or swapping an ancestor rejects the scan or
fresh apply comparison. Every owned descriptor closes on refusal and error.

Marker-looking links retain explicit marker-symlink refusal and blocking_marker.
The existing marker, packaged RECORD/source/bytecode and documentation checks
read through the same pinned namespace. Bounded captured RECORD bytes feed the
existing distribution parser; no candidate code or entrypoint is loaded.
The existing lease owner accepts a narrowly checked directory-relative identity
for cleanup, preserving bounded record parsing and the actual noncreating
kernel-lock probe. Missing or changed guarded records are unavailable.

Root/candidate links, foreign owners, hard links, current and registered
worktrees, namespace/toolchain pairing, native grace/census/PID/lease checks,
fresh fingerprints and exclusive receipt authority remain required. No
force option, alternate deleter, scanner, runner, cache or threshold is added.
Unsupported no-follow primitives preserve the namespace.

Actual deletion still uses the existing fd-safe shutil.rmtree with
avoids_symlink_attacks required. Ordinary interior links are unlinked.
A late raced directory replacement can cause the stdlib to open/fstat a
directory before rejecting descent; its guarantee is resistance to destructive
symlink traversal, not zero transient opens under every adversarial race.
The scanner and classification reader enforce the stronger no-target-open
boundary. A real fixture retains the native late-error/partial directory state,
writes no success receipt, and proves outside data survives.

The firsthand [CPython issue4489](https://bugs.python.org/issue4489),
[migrated issue48739](https://github.com/python/cpython/issues/48739), spans
2008-2012 and is resolved. It records ancestor-replacement races and a regression
in deleting directories containing symlinks, followed by fd/inode checks and
regression fixes. This supports distinguishing ordinary interior unlink from
top-level link refusal. It is not a current stdlib vulnerability finding or
proof of exploitation here. Current
[rmtree documentation](https://docs.python.org/3.11/library/shutil.html#shutil.rmtree)
and [fwalk documentation](https://docs.python.org/3.11/library/os.html#os.fwalk)
describe the mature descriptor facilities. CPython's
[3.11 fwalk implementation](https://github.com/python/cpython/blob/v3.11.14/Lib/os.py#L438)
also explains why the stricter scanner uses explicit no-follow opens.

Source acceptance and actual capacity recovery are separate. Retain
/tmp/gludd-v012-capacity-repair-6ade745 and its failed 96/95 native guard,
11 empty-directory receipts and unrelated UV-launcher refusal. No real cleanup
apply or unchanged hard-guard retry is evidence from the M16 fixtures.

## Root-route binding through native deletion (M17)

Independent review of immutable913ff57 withheld source approval: root discovery
reopened the validated path, and the heartbeat worker passed an absolute path
to rmtree after the scanner's root anchors had closed. A caller-root or ancestor
replacement could therefore select a different same-basename outside directory.

The separate child keeps the existing no-follow root anchor open for bounded
fd-scandir discovery and passes that descriptor into candidate classification.
Apply opens and checks the planned root, performs the immediate no-follow leaf
identity/uid check relative to it, and borrows the same descriptor through the
existing worker's completion or error. Native rmtree receives only candidate.name
and dir_fd; there is no path fallback. The anchor revalidates the root route
before the existing success receipt is published. A late route change can leave
truthful partial deletion of the original owned fixture, raises an error and
writes no false receipt; the replacement/outside tree is never selected.

The historical [CPython discussion](https://bugs.python.org/issue4489) above
motivated fd/inode checks and distinguishes top-level link refusal from interior
unlink. Current [rmtree's dir_fd contract](https://docs.python.org/3.11/library/shutil.html#shutil.rmtree)
and its [CPython3.11.14 entry path](https://github.com/python/cpython/blob/v3.11.14/Lib/shutil.py#L663-L740)
explain this caller obligation: the library first chooses the supplied root.
The repaired caller binds that choice to its already approved parent descriptor.
This resolved historical report is not a present stdlib defect or evidence of
exploitation in Gludd. The accepted native interior transient-open semantics
and the existing late-interior-race fixture remain unchanged.
