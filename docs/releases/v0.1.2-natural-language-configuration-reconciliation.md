the exact plan base. The foundation/hardening root supplies the canonical core,
the evaluator is grafted once after hardening, and the acceptance commits are
then replayed in source order. The later acceptance collection is the sole

same surface. No source branch is merged wholesale.

attestation head `84a314d05963519bab331981e1a0d8d86d96e42b`.

## Mechanical findings

`make git-show-commit` resolved every source commit and parent above. The
acceptance chain is linear through

d0591e43c826ddbbc9456f83a2fd0b09b82ccfd6 ->
84a314d05963519bab331981e1a0d8d86d96e42b`. The evaluator is a sibling of the
hardening tip because both have exact parent `11411449`; it is not a descendant
of `ad997d89`.

The plan base already contains `350434f5`: `make git-is-ancestor` returned
`exit=0` for `350434f5 -> 269106e7`. It returned `exit=1` for both
`f25fe50b -> 269106e7` and `5cc1c843 -> 269106e7`. The source manifest root is
therefore not replayed, while its acceptance child still is.

Whole-commit patch identity hides one important lower-level duplicate. The
resulting `ad997d89` blobs for `catalog.py`, `contracts.py`, and `planner.py`
are byte-for-byte the same blobs that `5ffb8178` independently adds. Their
full blob IDs are pinned in the inventory. Keeping the foundation side for
those three add/add conflicts loses no acceptance semantics and prevents a
second implementation of the core.

The ten collection paths are not blob-identical. The older foundation
collection permits remote HTTPS controller access, a legacy offline PSK escape
hatch, and host bounds greater than one. The acceptance collection instead
pins loopback-only controller authority, one host and one canary, canonical
digest change IDs, stable idempotency keys, fixed OpenBao path and mount,
`changed: false`, `mutation_performed: false`, and no legacy or ambient-secret
fallback. Those are deliberate contract differences, not mergeable variants.
The acceptance blobs win wholesale, and `085ebc7a` must then harden them.

The generic helper below `general_ludd.agent` and the narrower helper below
`general_ludd.configuration` are also not patch duplicates. The former permits
a normalized project-relative secret path for existing agent callers; the
latter hardcodes `gludd/controller_psk` and the `secret` mount for this
collection. Keep both source artifacts at this tranche rather than widening
the collection helper or inventing a third implementation.

and provider tests must agree on `changed: false` and
`mutation_performed: false`; check mode is a request property, not convergence
evidence.

Activation may begin only after the exact combined SHA passes the matrix:

1. Register the new surface at zero traffic while the previous route remains
   active.
2. Admit at most one plan-only tenant/profile against a loopback controller and
   an immutable local-provider identity.
3. Require serialized conformance, independent-file, runtime, catalog, model,
   and schema digests before accepting a receipt.
4. Keep status reads available when new plan intake is disabled. Host mutation
   count must remain zero throughout canary and rollback rehearsal.

Rollback is old-route-first and uses the result SHAs from the integration
receipt, not the historical source hashes:

1. Block new plan intake and disable the router, CLI, and collection entry
   points; continue digest-bound status reads.
2. Drain bounded read-only work and preserve every plan, status, evaluation,
   provider-conformance, attestation, and failure receipt unchanged.
3. Restore the last admitted route/generation before removing any candidate
   registration.
4. Revert result commits in reverse semantic order:
   `84a314d0`, `d0591e43`, `ea12b54b`, `e19b8ef4`, `0a173c0c`, `085ebc7a`,
   `df430280`, `2a22d811`, `f4ef07b5`, `5ffb8178`, `f25fe50b`, `43efab68`,
   `ad997d89`, `11411449`, then `5cc1c843`.
5. Re-run discovery, focused tests, coverage, and `make gate`. No host-state
   compensation is permitted or required because the admitted tranche never
   mutates a managed host.

Any inability to prove old-route restoration or receipt preservation is a
failed rollback, not permission to delete evidence or widen runtime authority.

## No-independent-recreation proof

The integration owner must append a receipt table containing source SHA,
result SHA, disposition, conflict action, and final blob ID. The table is
complete only when all of these invariants hold:

- `350434f5` is ancestry and is not replayed; `4d410148` is excluded as a
  superseded manifest-only snapshot.
- Every commit in `canonical_source_order` appears exactly once and no other
  natural-language source commit appears.
- The three core conflict paths equal the pinned foundation blob IDs. No
  reconciliation code is authored for them.
- The ten collection conflict paths equal the pinned acceptance final blob IDs
  after `085ebc7a`. No foundation/acceptance hybrid is accepted.
- The only shared-file union is the two already-authored target definitions and
  their two contract records, each present exactly once.
- All other production, test, fixture, and documentation paths are unchanged
  source patches from the selected commits. A reconciliation-only commit may
  update evidence documents, but may not add feature logic.
- `d0591e43` immediately precedes `84a314d0` in both the source ledger and the
  result ledger. Squashing or reversing them invalidates the proof.

These checks prove single-source selection at both commit and blob level. A
fresh implementation that merely resembles a source feature cannot satisfy
the ledger and is outside this plan.
