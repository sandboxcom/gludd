## Decision and Reconciliation

This document specifies how Gludd can implement a typed-decision adapter without
creating an OpenJev or Laya provider special case. It does not reverse the
[`provider admission decision`](../features/TYPED_DECISION_PROVIDER_ADMISSION.md):
v0.1.2 does not bundle an upstream package, image, SDK, model, or moving alias,
and no runtime profile is enabled until the decision's maturity and evaluation
gates pass.

The [`typed-decision backlog`](v0.1.2-typed-decision-backlog.md) remains the
delivery authority. TD12-01 through TD12-05 are the core. TD12-06 through
TD12-10 are optional expansions. This contract makes their boundaries concrete;
it does not mark any item implemented or authorize a canary.

Two deployment profiles may eventually use one adapter:

1. `jev_http_external`: an operator-managed HTTPS endpoint, including a pinned
   `razorback16/openjev` deployment. Gludd owns the client and leases, not the
   remote process or artifacts.
2. `model_worker_jev_http`: an exact Laya release and checkpoint inside a
   Gludd-owned universal model-worker generation. The Gludd daemon does not
   import Laya; the worker presents the same bounded wire contract.

No `openjev` or `laya` provider preset is added. Backend names are profile data,
never task-policy branches. A second independent Jev-shaped implementation must
pass the same fixtures before production admission proves provider neutrality.

## Ownership and Pinning

| Asset | Owner | Immutable admission identity | Update authority |
|---|---|---|---|
| Normalized request, result, reason codes, and adapter | Gludd typed-decision owner | Contract and normalization version plus source digest | Reviewed Gludd change only |
| Profile and capability evidence | Gludd compatibility owner | Profile digest plus TD12-01 identity fingerprint | Two-person profile review |
| Corpus, calibration, and thresholds | Gludd evaluation owner | Corpus, calibration, method, and tool digests | Fresh held-out evaluation |
| Redaction rules and receipts | Gludd security owner | Sanitizer version and rule digest | Security review and adversarial fixtures |
| Local worker generation | Gludd lifecycle owner | Source archive, image, runtime, model, tokenizer, renderer, and calibration digests | Blue/green model-worker update |
| External endpoint | Operator | HTTPS origin/trust class plus attested backend identity | Operator changes endpoint; Gludd re-admits identity |
| OpenJev/Laya source and weights | Upstream | Full commit and content digests recorded by Gludd | Upstream cannot auto-update Gludd |

Tags, branches, `main`, `latest`, `openjev-latest`, `jev-latest`, floating Hub
revisions, mutable image tags, and an endpoint's displayed model name are never
identity. A release tag is useful provenance only after Gludd resolves it to a
full commit and verifies every artifact digest. An upstream patch carried by
Gludd becomes a separately owned patch artifact with its own digest and review;
silent local edits are forbidden.

The example bundle deliberately uses sentinel digests and `example_only: true`.
It demonstrates the schema but is mechanically ineligible for admission.

## Proposed Implementation Boundaries

The first implementation must stay within these candidate modules; equivalent
names are allowed only if the dependency directions remain the same:

| Candidate module | Owns | Must not own |
|---|---|---|
| `typed_decisions/contracts.py` | Pure request, question, result, capability, reason, and identity types | HTTP, model imports, thresholds, task policy |
| `typed_decisions/normalization.py` | Jev-shaped encode/decode and semantic validation | Endpoint selection, retries, authorization |
| `typed_decisions/transport.py` | Bounded HTTPS/model-worker call and error mapping | Provider names, calibration, process creation |
| `typed_decisions/profiles.py` | Strict profile parsing, digests, compatibility, update diff | Secret values, downloads, mutable aliases |
| `typed_decisions/sanitization.py` | Pure copy-on-write redaction and immutable observer receipts | Dynamic callbacks, result replacement, forwarding |
| `typed_decisions/scheduling.py` | Optional schema grouping, deadline-aware fan-out, residency requests | Model-specific batching or eviction |
| `infra/typed_decision_lifecycle.py` | Adapter binding to universal model-worker leases/generations | A parallel daemon supervisor |

Only `failure_classification` is eligible initially. `SmallModelTaskPolicy`
continues to determine task eligibility; the adapter cannot grant execution,
mutation, credential, deployment, completion, security, or release authority.

## Canonical Request Contract

Gludd sends the conservative common subset of `POST /v1/systemone`:

```json
{
  "model": "an-exact-nonmoving-model-id",
  "state": "bounded and sanitized state",
  "questions": {
    "failure_kind": {
      "type": "choice",
      "instructions": "Classify the observed failure.",
      "criteria": {
        "capacity": "A bounded resource was exhausted.",
        "configuration": "Configuration is invalid.",
        "transient": "A retryable dependency failed.",
        "unknown": "Evidence does not support another label."
      }
    }
  }
}
```

The adapter emits no upstream extension in v1: no images, `steps`, `samples`,
`think`, `sequential`, hook, task, language-autodetection, or routing field.
Input is bounded before redaction and again after redaction. Question IDs and
criteria order are stable. A tokenizer-specific limit is a capability bound;
Gludd rejects an over-limit request instead of relying on Laya/OpenJev's
different truncation behavior.

The outbound object is closed. Upstream request tolerance for unknown fields is
irrelevant because Gludd never emits them. `state` may be a string, object, or
array only after the profile proves identical normalization behavior for that
shape; the first profile permits strings only.

## Wire-to-Gludd Normalization

Every response is decoded against the original request, not by trusting the
response's labels or question order.

| Wire type | Required upstream fields | Canonical Gludd value | Mandatory validation |
|---|---|---|---|
| `choice` | `choice`, `probabilities`; `confidence` is optional metadata | Ordered label/probability vector and selected label | Exact question ID and label set; finite `[0,1]` values; sum within `1e-4`; top label agrees with `choice` within declared tie rule |
| `noul` | `noul = P(true)` | Ordered `false`, `true` vector and Boolean top outcome | Finite `[0,1]`; derive only `1-p` and `p`; no invented confidence |
| `score` | `score`, `probabilities`, `legend`; `confidence` is optional metadata | Ordered level probabilities and expected numeric score | Exact `0..n-1` keys and legend; 2-10 levels; recomputed expectation within `1e-4` |

Upstream `confidence` is retained as redacted, non-authoritative metadata. It is
never converted into Gludd confidence, threshold, abstention, or authorization.
TD12-04 calculates calibration from raw normalized probabilities for an exact
identity, option-count bucket, language/domain slice, and corpus.

`usage.input_tokens`, `usage.output_tokens`, and `Server-Timing` are advisory
telemetry. They cannot relax byte/token/deadline budgets. Unknown additive
top-level metadata may be retained in a size-bounded opaque field in shadow
receipts. Unknown answer fields are non-authoritative; missing required fields,
extra/missing question IDs, type changes, non-finite values, or identity mismatch
invalidate the entire response. Partial answers never partially influence Gludd.

Normalization emits one of these stable reason codes:

```text
valid, request_invalid, request_unsupported, request_redaction_failed,
identity_mismatch, capability_mismatch, response_malformed,
response_semantic_mismatch, auth_failed, endpoint_unavailable, overloaded,
rate_limited, deadline_exceeded, cancelled, capacity_rejected
```

HTTP `400/422` maps to request-invalid or unsupported only after bounded error
decoding; `401/403` to auth-failed; `404` to capability-mismatch; `429` to
rate-limited; `503` to endpoint-unavailable; `529` to overloaded; other `5xx`
to endpoint-unavailable. No adapter retry occurs in v1. All failures use the
current Gludd path and expose no raw body, endpoint, credential, state, or answer.

## Capability Negotiation and Readiness

There is no trusted standardized capability endpoint across these projects.
Negotiation is the intersection of:

1. the reviewed immutable profile;
2. static facts extracted from the pinned source/model artifacts;
3. a bounded runtime inventory such as `GET /v1/models`; and
4. an exact known-answer readiness probe through the normal transport.

Runtime discovery can remove a capability but cannot add one. Model listing is
not readiness: OpenJev documents routed models that remain listed while their
container is stopped and returns `503` when invoked. Any source, model, limit,
question-type, state-shape, truncation, probability, or runtime mismatch marks
the generation unavailable and produces no shadow call.

The v1 common capability is text-only Choice, Noul, and Score; 32 questions per
request; 20 Choice options; 2-10 Score levels; no upstream truncation; no
extensions; one exact model identity. These are Gludd limits, not claims about
larger upstream maxima. A capability increase requires a new profile digest,
fixtures, corpus slices, and calibration evidence.

## Batching and Residency

Batching is disabled initially. When TD12-07 is admitted, requests group only by
identity fingerprint, contract/schema version, exact question-schema digest,
token budget, calibration digest, trust/sensitivity class, and deadline bucket.
The scheduler restores original order and maintains per-request receipts. A
batch failure falls back to bounded individual calls only within each original
deadline. Cross-tenant or cross-sensitivity batching is forbidden.

For OpenJev external profiles, Gludd owns concurrency, queue, and client leases
but makes no residency claim. OpenJev's internal question chunking is opaque and
must not change normalized semantics.

For Laya model-worker profiles, TD12-08 issues only universal lifecycle intents:
preload an exact identity, lease it, drain it, and retire it. Gludd never calls
Laya's router cache, `gc.collect`, or device cache APIs from policy. No leased or
in-flight generation may be evicted. Measured resident bytes and device
headroom, not upstream estimates, govern admission.

## Redaction and Injection Boundary

Hosted transport requires a versioned sanitizer. It operates on a copy before
serialization and returns only rule identifiers, counts, and digests. A timeout,
exception, unknown rule, or unresolved protected value fails closed before any
network byte is sent. An attested local profile may select an explicit
no-redaction profile with its own digest.

Observers receive immutable normalized results and may emit bounded metrics.
They cannot modify request/result, route, identity, threshold, fallback,
authority, or lifecycle. Laya's mutable prediction hooks are not exposed,
imported, or accepted through configuration. State, instructions, answers, and
backend error text remain untrusted data and cannot install behavior.

## Compatibility and Migration Rules

- `gludd.typed-decision-adapter-contract/v1` is strict. A reader rejects an
  unknown major version and a profile with unknown security or authority fields.
- Additive observational metadata may be ignored only when size-bounded and
  explicitly non-authoritative. A semantic field addition changes the profile
  and normalization digest.
- A source, model, tokenizer, renderer, scoring, calibration, runtime, endpoint
  trust, redaction, or normalization change creates a new identity. It never
  updates an admitted identity in place.
- Stored receipts retain their original schema and identity. New readers keep a
  fixture-tested decoder for the supported evidence window; receipts are never
  rewritten to resemble new predictions.
- A future database change must be expand/contract: deploy additive nullable
  fields/readers first, dual-read, switch writers, drain old readers, then remove
  only in a later release. v0.1.2 requires no database migration.
- One profile may move `disabled -> shadow -> 1% -> 5% -> 25%`. It may move
  backward at any time; no schema migration is required for rollback.

## Exact Update and Review Workflow

Every upstream update is a reviewed Gludd pull request and follows this order:

1. Resolve the requested tag/ref to a full commit. Fetch an immutable source
   archive; record its SHA-256, license, release notes, security policy, and all
   submodule/patch/runtime inputs. Reject force-moved or unverifiable refs.
2. Resolve model, tokenizer, renderer, calibration, container/base image, Python,
   inference runtime, and adapter inputs to content digests. Generate an SBOM;
   scan source, image, dependencies, and licenses. No credential enters build.
3. Diff observed wire schemas and capabilities against the prior profile.
   Classify each delta as observational, additive-compatible, identity-changing,
   breaking, or security-relevant. Breaking/unknown changes stay disabled.
4. Run the upstream suite in a disposable no-secret environment as supporting
   evidence. Upstream green never substitutes for Gludd tests.
5. Validate the contract schema and examples; run all adapter unit/fixture,
   mutation, metamorphic, redaction, queue, cancellation, and update-diff tests.
6. Re-run the frozen Gludd corpus and calibration harness for the new identity.
   Compare every slice, latency, throughput, and measured memory with current
   and prior candidates. Published upstream benchmarks are not promotion data.
7. Build and attest a green model-worker generation, or attest the new external
   endpoint, without changing traffic. Execute readiness and fault probes.
8. Obtain compatibility, security, evaluation, and lifecycle owner approvals.
   The same person cannot author and solely approve the source/profile update.
9. Enable shadow traffic by exact digest. After TD12-05 windows pass, an
   operator may advance the bounded canary; there is no automatic promotion.
10. Exercise rollback to the prior identity, drain green, destroy Gludd-owned
    resources, and prove absence before the update is complete.

An urgent upstream security advisory causes immediate disablement/demotion.
Gludd can fall back without first finding or deploying an updated candidate.

### Offline atomic plan and receipt tranche

The v0.1.2 checker now implements only the pre-admission evidence step in
`scripts/check_typed_decision_adapter_update.py`. `build_prepared_update()`
accepts an already-local schema plus exact old and new profiles. It succeeds only
for `COMPATIBLE_PINNED_UPDATE`; a no-op, example profile, enabled/shadow profile,
moving or sentinel pin, protected-contract change, or unknown input fails closed.
It never resolves a ref, fetches an archive, contacts an endpoint, loads a model,
or changes runtime admission.

The prepared document is canonical ASCII JSON with sorted keys and SHA-256
identities. Its immutable, typed components bind the following evidence:

| Component | Digest-covered content |
|---|---|
| Compatibility evidence | Exact schema/old-profile/new-profile digests, checker status, sorted changed pin paths, and the protected sections proven unchanged |
| Rollback metadata | Exact old profile digest, profile ID, identity fingerprint, source commit/archive digest, mandatory `disabled` target, and `required: true` |
| Update plan | Event/time, hashed actor identity, exact old/new pin summaries, evidence, rollback, fixed evidence-only actions, and three false runtime/network/admission flags |
| Receipt | Plan/evidence/rollback digests, event/time, hashed actor identity, `prepared` status, explicit redacted fields, and the same three false flags |

The raw actor ID, credentials, transport endpoint, request state, and prediction
answers are absent from receipts. Replay supplies the same schema and exact old
and new profiles, reconstructs every component, and requires canonical document
equality. A missing field, unknown field, changed digest, unsafe flag, weakened
rollback, or different pin therefore fails closed instead of being tolerated as
an older receipt shape.

`persist_prepared_update()` is bounded to 256 KiB and creates a mode-`0600`
sibling temporary file, flushes and syncs it, then uses an atomic no-overwrite
link and syncs the parent directory. Exact-byte replay returns `UNCHANGED`
without touching modification time. A different existing document, symlink,
non-regular file, permissive existing mode, missing/symlinked parent, write race,
or incomplete cleanup is an error; it never overwrites evidence. This tranche
does not authorize shadowing, canaries, database writes, migrations, deployment,
or traffic changes. Those remain behind the admission decision and the acceptance
matrix below.

## ZDD and Rollback

Blue remains authoritative while green is fetched, built, attested, evaluated,
and readied. Green starts disabled, then shadow. The generation/profile pointer
switch is atomic; each in-flight request retains the identity, sanitizer, and
calibration it started with. Disabling selection stops new candidate calls
within 10 seconds and never waits on the candidate before returning the primary
result.

Rollback atomically selects current-path/shadow authority, drains bounded calls,
retires and destroys owned green resources, releases client/credential/model
leases, and records absence proof. The previous healthy generation stays until
green completes its canary and rollback drill. Receipts and evaluation reports
are append-only evidence and are not downgraded or rewritten.

### Molecule

The hermetic `typed_decision_laya_worker` scenario must use a tiny fixture server,
not download weights. It covers `create -> converge -> idempotence -> verify ->
side_effect -> verify -> destroy` and proves:

- exact source/image/model digests render into a namespaced worker generation;
- check mode and a second converge change nothing;
- blue serves while green is installed and readied;
- missing identity, failed probe, port conflict, and capacity pressure never
  publish green;
- drain preserves in-flight leases; destroy removes service, port, cache lease,
  credentials, temporary files, and generation; and
- external OpenJev profiles never create/destroy remote infrastructure.

### Hermetic and Optional Live E2E

`tests/e2e/test_typed_decision_shadow.py` runs fake OpenJev and Laya-shaped
servers through the same adapter. It must cover all question types, profile
swap, schema mismatch, truncated/missing answers, listed-but-unready `503`,
overload `529`, timeout, cancellation, restart, queue saturation, redaction
failure, demotion, rollback, and absence proof. The production answer must be
byte-identical with the feature disabled, shadow healthy, and every failure.

Live OpenJev/Laya tests are optional, manual, pinned, credential-isolated, and
non-blocking until the admission decision reopens. Before a canary they become a
release evidence requirement for the exact identity, but required CI remains
network-free and weight-free.

### Quantitative Gates

- New production files: at least 85% aggregate line and branch coverage and at
  least 75% for every individual file; no changed file may lower repository
  aggregate coverage below 85%.
- Normalization fixture agreement: 100%; malformed/identity/redaction fixtures
  fail closed: 100%; shadow influence on production output: 0 cases.
- Seeded secret removal before hosted send: 100%; false redaction on reviewed
  safe tokens: below 1%; observer mutation/injection successes: 0.
- Healthy bookkeeping overhead: no more than 5 ms p95 and 1 MiB steady-state per
  worker. No leaked tasks, sockets, processes, ports, files, or leases.
- Warning-free lint, strict typing, warnings-as-errors tests, security scans,
  focused coverage, Molecule, E2E, rollback drill, and the full project gate all
  pass before runtime promotion. Documentation alone does not claim these gates.

## Upstream Evidence and Freshness Caveat

Primary sources reviewed 2026-09-27:

- [`razorback16/openjev` README][openjev-readme] documents the wire shapes,
  aliases, extensions, `400/422/429/529` behavior, internal question chunking,
  Laya routing, silent encoder truncation, probability rounding, resource
  estimates, pinned vLLM patches, and routed-model `503` readiness gap.
- [Laya README][laya-readme], [router][laya-router], and [agent][laya-agent]
  document exact Hub revisions, language/checkpoint routing, schema-grouped
  batch execution, mutable hooks, preload/LRU behavior, and bounded batches.
- Laya issue [#32][laya-32] reports Jev-wire strictness differences; issue
  [#384][laya-384] reports silent dictionary-state language misrouting; issue
  [#394][laya-394] shows confidence thresholds do not transfer across option
  counts; issue [#433][laya-433] records duplicate hook invocation; issue
  [#285][laya-285] records benchmark drift as runtime/checkpoints change.
- OpenJev issues [#4-#6][openjev-issues] are early practitioner requests for
  comparative and reproducible benchmark evidence.

The ecosystem still has no long-lived public production issue history: the
linked repositories and practitioner reports were days old when reviewed. That
absence is itself an admission constraint, not positive stability evidence.
The ninety-day/two-stable-release/security-policy gate remains unresolved.
Source pages are observations, not promises; every update must repeat this
review and replace source links with immutable commit links in its evidence.
