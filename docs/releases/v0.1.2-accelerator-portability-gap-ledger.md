## Scope and evidence rules

This ledger compares current upstream documentation and issue reports with the
accelerator contracts present in Gludd's v0.1.1 capability baseline. It defines
requirements for a future v0.1.2 candidate; it does not add a launcher, change a
provider, reserve capacity, or authorize a release.

No live accelerator proof is established.
No multi-device runner proof is established.
No TPU runtime proof is established.
Planning and hermetic fixtures are not live execution evidence. Upstream
documentation establishes an upstream interface only; it does not establish
that Gludd renders, executes, observes, or rolls back that interface correctly.

Facts below are dated by the upstream page's stated update date when available,
otherwise by the 2026-09-28 review date. Practitioner reports are
version-scoped regression hypotheses. An open issue is not proof of a universal
defect, and a closed issue is not proof that Gludd's eventual pin contains a fix.

## v0.1.1 capability baseline

The [v0.1.1 release note](v0.1.1.md) says that release changed documentation and
metadata only and made no functional change from its predecessor. Accordingly,
this ledger maps the current documented baseline rather than inferring live
capability from a version label:

- [Accelerator discovery](../features/ACCELERATOR_DISCOVERY.md) normalizes
  read-only local and Slurm observations for several accelerator kinds. It does
  not provision hardware or start a model. TPU discovery uses JAX, records an
  unknown memory value where JAX cannot supply one, and rejects silent CPU
  fallback.
- [Accelerator topology](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) is a pure
  planner. It can represent GPU and TPU shapes, render vLLM parallelism counts,
  and describe runner-managed Ollama or TPU placement. It explicitly requires
  post-load verification for runner-managed placement.
- [Azure GPU VM strategy](../features/AZURE_GPU_VM_STRATEGY.md) uses inventory,
  capacity observations, exact SKU facts, and attestation to choose between a
  one-device Container Apps shape, one multi-device VM, or VMSS. Its automated
  proof uses SDK-shaped fakes.
- [Azure live-proof design](../design/AZURE_ACCELERATOR_LIVE_PROOF.md) remains
  proposed and says that plans, mocks, credentials, HTTP responses, and
  `nvidia-smi` alone are not live model-serving proof.

The baseline therefore supports discovery, fail-closed planning, and hermetic
contract tests. It does not establish a paid provider allocation, runner
execution, model correctness, per-device placement, collective communication,
or rollback drill on accelerator hardware.

## Gap ledger

### 1. vLLM multi-GPU execution

**Dated upstream facts.** The current vLLM
[parallelism guide](https://docs.vllm.ai/en/latest/serving/parallelism_scaling/),
reviewed 2026-09-28, documents tensor parallelism for a single multi-GPU node
and combined tensor/pipeline parallelism across nodes. It recommends pipeline
parallelism when a model does not divide evenly or the node lacks NVLink, and it
requires identical environments plus private, trusted networking for Ray. The
current [serve CLI](https://docs.vllm.ai/en/latest/cli/serve/) constrains the
local multiprocessing world size to available GPUs, documents physical device
IDs or UUIDs, and notes that its device-ID option does not control Ray placement
groups. A reporter in
[vLLM issue #33041](https://github.com/vllm-project/vllm/issues/33041), opened
2026-01-25 and closed by the review date, described a specific dual-Blackwell
setup that served on one GPU but hung after NCCL initialization at tensor
parallel size 2.

**Gludd inference.** A syntactically valid tensor- or pipeline-parallel plan is
not an admission decision. Topology, model divisibility, quantization, worker
backend, CUDA, NCCL, driver, device identity, and the communication path belong
to one immutable candidate tuple. Ray traffic needs an isolated private network
and must not expose credentials or unencrypted control traffic to an untrusted
segment.

**v0.1.1 mapping.** The [topology
contract](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) can calculate vLLM
tensor- and pipeline-parallel counts and reject oversubscription, while
[discovery](../features/ACCELERATOR_DISCOVERY.md) can report local devices. It
does not start vLLM, exercise NCCL, confirm Ray placement, or retain a successful
multi-GPU inference receipt.

**Missing v0.1.2 requirement.** Add an opt-in admission contract that binds the
exact vLLM build, model and immutable model digest, quantization, worker backend,
OS image, GPU UUIDs, topology, CUDA, NCCL, driver, TP/PP shape, host count, and
network policy. The route stays disabled by default until the exact tuple passes;
an unrecognized topology or changed identity must fail closed without a
single-GPU or CPU fallback.

**Test/proof required.** Hermetic tests must cover divisibility,
oversubscription, no-NVLink selection, Ray device-ID limitations, and hostile
network configuration. An opt-in hardware test must launch the exact tuple,
exercise health and inference, compare the expected output digest and model
identity, record every worker/rank/device assignment and memory observation,
demonstrate the intended collective path, reject excluded devices, drain, and
repeat after rollback. A single successful HTTP response is insufficient.

**Residual/provider boundary.** vLLM owns runner semantics; NVIDIA and the OS
image own portions of the driver and collective stack; the cloud or operator
owns hardware and network capacity. Gludd can validate an observed tuple but
cannot guarantee that another model, quantization, GPU generation, region, or
upstream release behaves the same way.

### 2. Ollama GPU selection

**Dated upstream facts.** Ollama's current
[GPU guide](https://docs.ollama.com/gpu), reviewed 2026-09-28, documents
`CUDA_VISIBLE_DEVICES` for limiting NVIDIA devices, `ROCR_VISIBLE_DEVICES` for
AMD, and `GGML_VK_VISIBLE_DEVICES` for Vulkan; it recommends stable UUIDs over
numeric ordering and documents disabling the Vulkan backend when required.
[Ollama issue #9722](https://github.com/ollama/ollama/issues/9722), opened
2025-03-13 and still open at review, reports that Ollama 0.6.0 ignored a requested
CUDA-visible subset/order in one three-GPU environment.
[Issue #16592](https://github.com/ollama/ollama/issues/16592), opened 2026-06-07
and closed 2026-06-18, reports selection behavior in Ollama 0.30.6 that changed
when Vulkan probing was disabled. These reports describe their exact versions
and machines, not every Ollama installation.

**Gludd inference.** Environment-variable rendering alone cannot prove which
backend discovered a device or where model layers and cache reside. Admission
must compare requested UUIDs with observed process/backend placement after model
load and after a real request. A mixed CUDA/Vulkan or ROCm/Vulkan environment is
an explicit candidate dimension, never an invisible fallback.

**v0.1.1 mapping.** The [topology
contract](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) deliberately leaves
Ollama multi-device distribution to the runner and requires post-load
verification. It provides no implementation that pins an Ollama/backend version,
observes allocation per device, or blocks a route after placement drift.

**Missing v0.1.2 requirement.** Define backend-specific selection inputs,
canonical UUID ordering, allowed and excluded devices, Vulkan policy, model
digest, context and concurrency settings, and the required post-load
observation. Reject numeric-only identities when stable UUIDs are available and
keep the route disabled by default if observation does not match the request.

**Test/proof required.** Hermetic tests must cover NVIDIA, AMD, Vulkan, mixed
backend, reordered enumeration, stale UUID, excluded-device, insufficient-fit,
and CPU-fallback cases. An opt-in hardware test must pin the Ollama build and
backend, load the exact model, issue inference, record Ollama's processor report
plus independent per-device memory/utilization, prove excluded devices remain
unused, repeat after restart, and capture a safe unload/drain receipt.

**Residual/provider boundary.** Ollama owns scheduling and layer placement;
backend libraries and drivers own device enumeration; the operator owns the
host and its other workloads. Gludd can reject a mismatched observation but
cannot promise an upstream scheduler's future placement or prevent unrelated
host processes from using a device.

### 3. Azure Container Apps GPU limits

**Dated upstream facts.** Microsoft's
[serverless GPU overview](https://learn.microsoft.com/en-us/azure/container-apps/gpu-serverless-overview),
updated 2026-09-24, says that only the first container in a Container Apps app
receives the GPU and that multi-GPU and fractional-GPU replicas are unsupported.
It also records platform-managed driver/CUDA transitions and limited regional
availability. The [quota
reference](https://learn.microsoft.com/en-us/azure/container-apps/quotas), also
updated 2026-09-24, describes subscription/region and environment GPU quotas
whose exhaustion can prevent creation or scaling.
[Azure Container Apps issue #1511](https://github.com/microsoft/azure-container-apps/issues/1511),
opened 2025-06-10 and open at review, reports intermittent T4 job executions
that created a pod but failed before image pull in one region/profile.

**Gludd inference.** Container Apps is a one-GPU-per-replica, first-container
scale-out target. It is not a cross-replica tensor-parallel fabric. A profile
name, visible quota, successful deployment, or created replica is not proof that
the image started with a compatible driver/runtime and completed inference.

**v0.1.1 mapping.** The [Azure GPU VM
strategy](../features/AZURE_GPU_VM_STRATEGY.md) admits Container Apps only for a
whole isolated device that fits the workload, and the [topology
contract](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) rejects a request for
more than one device per Container Apps workload. Those are strategy and
hermetic-shape checks, not a live replica receipt.

**Missing v0.1.2 requirement.** Bind region, environment, workload profile,
quota observation, image digest, first-container index, single-device shape,
platform driver/CUDA observation, model fit, scaling limits, and egress policy.
Reject fractional or greater-than-one device requests locally. Multiple replicas
may scale independent whole-model requests only; they must never be presented as
one model-parallel worker group.

**Test/proof required.** Hermetic tests must reject second-container GPU access,
fractional devices, multi-device replicas, cross-replica TP/PP, unsupported
regions, and stale quota observations. An opt-in paid test must provision the
exact profile, verify only the intended first container sees one device, attest
driver/runtime/model identity, serve a request, scale independent replicas,
exercise a quota/capacity failure, drain, and delete only test-owned resources.

**Residual/provider boundary.** Azure owns region inventory, quota approval,
capacity, placement, platform patches, driver rollout, and control-plane
availability. Gludd cannot make quota equal capacity or freeze platform-managed
patch versions; it can pin observations, reject drift, and preserve failure
receipts.

### 4. Azure GPU VM attachment and topology

**Dated upstream facts.** Azure's current
[ND-family specification](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/gpu-accelerated/nd-family),
reviewed 2026-09-28, describes GPU count and fabric as properties of each VM
size. For example, an ND A100 v4 VM has eight A100 GPUs connected with NVLink
and dedicated InfiniBand paths. The [VM resize
guide](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/resize-vm),
reviewed 2026-09-28, says resizing a running VM restarts it and may require
deallocation when the target size is unavailable on the current cluster. The
[GPU driver extension
guide](https://learn.microsoft.com/en-us/azure/virtual-machines/extensions/hpccompute-gpu-linux),
reviewed 2026-09-28, says extension installation can reboot the VM and does not
automatically update installed drivers.
[WALinuxAgent issue #1938](https://github.com/Azure/WALinuxAgent/issues/1938),
opened 2020-07-08 and still open at review, records a long-lived package-manager
race between cloud-init and extensions on an affected Ubuntu/agent combination.

**Gludd inference.** A GPU is not a detachable Gludd resource. Requested count,
memory, GPU generation, NVLink/Infinity Fabric, RDMA, NUMA, and VM generation
must resolve to one exact SKU and then be re-attested inside the guest. Changing
that shape is a replacement generation rollout; in-place resize is a disruptive
provider operation and cannot satisfy ZDD by itself.

**v0.1.1 mapping.** The [Azure GPU VM
strategy](../features/AZURE_GPU_VM_STRATEGY.md) normalizes exact SKU inventory
and chooses a host-local multi-device VM where appropriate. The [topology
contract](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) can represent
interconnect and device count. Its tests use provider-shaped fakes and do not
attest a real guest, NVLink/RDMA path, runner collective, or capacity allocation.

**Missing v0.1.2 requirement.** Remove any attach/detach interpretation and bind
the plan to subscription, region, zone, exact SKU/generation, image digest,
driver method/version, device UUIDs, guest topology, RDMA capability, runner
tuple, and ownership tags. Provision a new generation, attest it before traffic,
and retain the old generation for drain and rollback.

**Test/proof required.** Hermetic tests must cover SKU retirement, wrong GPU
count, fractional SKU, absent fabric, resize/restart semantics, extension reboot,
package-lock contention, and stale inventory. An opt-in paid test must allocate
the exact SKU, capture guest device UUIDs and topology, validate the intended
NVLink/RDMA/NCCL path where requested, serve the pinned model across all intended
devices, canary, shift traffic, drain, roll back to the old generation, and
delete only the new Gludd-owned resources.

**Residual/provider boundary.** Azure owns allocation, physical host/fabric,
firmware, capacity, and some maintenance events; the image/extension publishers
own driver packages; the operator owns credentials and policy. SKU documentation
does not prove a subscription can allocate it or that a particular guest sees
the documented healthy topology.

### 5. TPU and runtime portability

**Dated upstream facts.** The current vLLM TPU
[installation guide](https://docs.vllm.ai/projects/tpu/en/latest/getting_started/installation/),
reviewed 2026-09-28, installs a separate `tpu-inference` distribution and checks
the vLLM version, plugin version, selected platform, JAX backend, and TPU device
coordinates. Its [feature
matrix](https://docs.vllm.ai/projects/tpu/en/latest/features/), reviewed the same
day, marks multi-host DP, EP, and TP as untested in its release matrix and shows
runtime- and release-specific differences for TP and quantization. The current
[PyTorch/XLA PJRT runtime
guide](https://docs.pytorch.org/xla/master/runtime.html) uses an explicit
`PJRT_DEVICE` and documents different process/thread layouts across TPU
generations. Google Cloud's [TPU software-version
guide](https://docs.cloud.google.com/tpu/docs/runtimes), updated 2026-09-24,
maps runtime images to TPU generations, says the legacy Cloud TPU API is not
supported on TPU7x and later, and records generation/framework limitations.
Its [TPU architecture
guide](https://docs.cloud.google.com/tpu/docs/system-architecture-tpu-vm),
reviewed 2026-09-28, defines a slice as chips connected within a pod and records
generation-dependent two- or three-dimensional topologies and host boundaries.
[vLLM issue #20869](https://github.com/vllm-project/vllm/issues/20869), opened
2025-07-13 and closed as not planned by review, reports that a specific
encoder-only embedding model could not use the then-available TPU Pallas
attention path.

**Gludd inference.** `kind: tpu` is insufficient portability metadata. TPU
generation/slice, provider lifecycle API, topology/mesh, plugin and vLLM pin,
JAX/XLA/PJRT runtime, process model, model architecture, dtype, quantization,
kernel, and requested features form one candidate. A GPU launch renderer cannot
be relabeled as a TPU launcher, and a JAX device listing must not be treated as
model-serving evidence.

**v0.1.1 mapping.** [Accelerator
discovery](../features/ACCELERATOR_DISCOVERY.md) can identify a TPU through JAX,
record its platform, and reject a CPU fallback. The [topology
contract](../features/ACCELERATOR_TOPOLOGY_CONTRACT.md) can carry an opaque TPU
shape but leaves mesh and launch behavior runner-managed. No current Gludd
provider lifecycle or launch proof establishes TPU inference.

**Missing v0.1.2 requirement.** Define a separate, disabled-by-default TPU
runtime adapter with exact provider, generation, slice, topology, plugin,
runtime, image, model, feature-matrix, precision, quantization, and mesh
admission. Unsupported or untested feature combinations must fail closed; there
is no automatic CPU, GPU, alternate model, or alternate-runtime fallback.

**Test/proof required.** Hermetic matrices must cover generations, slices,
single/multi-host shapes, PJRT process layouts, plugin/version drift, CPU
fallback, model architecture, structured decoding, embedding, quantization, and
unknown memory. An opt-in paid test must create an exact test-owned slice,
attest every device/process/coordinate and runtime pin, load and serve the exact
model, exercise the requested mesh/features, verify output and no fallback,
drain, destroy the slice, and retain cleanup and cost receipts.

**Residual/provider boundary.** The TPU provider owns quota, capacity, topology
allocation, maintenance, and lifecycle APIs; vLLM TPU, JAX, XLA, and PJRT own
different runtime layers; model and kernel support changes by release. Gludd can
admit a pinned observed combination only, not portability across untested
generations, runtimes, models, or future upstream releases.

## Cross-provider requirements

A future implementation must meet every requirement below before any topic can
leave `gap_open`:

1. Use an immutable candidate identity containing provider, region/host,
   accelerator kind/generation, device UUIDs or coordinates, topology, runtime,
   runner/plugin, driver, model digest, precision/quantization, and feature set.
2. Separate discovery, planning, allocation, guest attestation, runner launch,
   model load, inference, promotion, drain, rollback, and cleanup receipts. No
   earlier phase can stand in for a later one.
3. Compare requested and observed identities after allocation and after model
   load. Missing, extra, reordered, CPU-fallback, or runner-selected devices fail
   closed unless the exact behavior was explicitly admitted.
4. Keep live tests opt-in, budgeted, namespaced, least-privileged, and scoped to
   test-owned resources. Never print credentials, raw prompts, provider tokens,
   or tenant workload content.
5. Pin upstream version/status observations by review date. A mutable `latest`
   page or closed issue cannot promote a candidate without a fresh receipt.

## Security and privacy

- Ray or other distributed control/data traffic is permitted only on a private,
  authenticated, least-privileged network boundary. Public or ambiguous worker
  discovery fails closed.
- Provider credentials stay in the provider boundary and are never copied into
  runner arguments or receipts. Receipts keep hashes, stable reason codes, and
  redacted resource identities rather than tokens, prompts, or model output.
- Device and topology evidence may expose host inventory. Store only the minimum
  normalized identity required for replay, protect access, and apply the
  project's evidence-retention policy.
- Runtime images, model artifacts, extensions, plugins, and drivers require
  immutable digests or exact versions plus provenance checks. Mutable tags do
  not satisfy admission.
- Unknown accelerator identity, feature support, model fit, placement, fallback,
  or cleanup state blocks promotion rather than broadening authority.

## ZDD and rollback

All five routes remain disabled by default. Zero-downtime deployment means the
current authoritative route stays live while a new, namespaced generation is
created and attested; it does not mean an in-place device mutation is harmless.

1. Create a test or canary generation without changing current traffic.
2. Verify allocation, guest/runtime identity, model load, inference, device
   placement, and observability against the immutable candidate.
3. Shift only bounded canary traffic, watch error/latency/resource thresholds,
   then advance gradually. Any missing signal fails closed.
4. On failure, stop new canary traffic, restore the old route, drain the new
   generation, preserve receipts, and remove only Gludd-owned resources.
5. Keep operator-owned devices, clusters, endpoints, models, networks, and
   provider-owned platform components untouched. Provider cleanup failure is a
   retained incident, not permission to delete a broader resource group.

For Azure VM shape changes, rollback means returning traffic to the retained old
VM/VMSS generation; it never means attaching a GPU or resizing the serving VM in
place. For Container Apps, rollback restores the previous revision/profile
tuple. For local Ollama/vLLM, it restores the old namespaced runner and device
lease. For TPU, it restores the previous route before destroying only the
test-owned slice.

## Residual provider boundaries

- Provider documentation can change after the review date. Region lists,
  profiles, SKU availability, quotas, runtime matrices, driver versions, and
  issue status must be refreshed without treating change as proof.
- Quota is permission to request capacity, not a capacity reservation. A plan
  must distinguish inventory visibility, quota, allocation, guest attestation,
  and completed model inference.
- Cloud providers control placement, host maintenance, physical topology,
  platform patches, and some failure recovery. Gludd owns only its request,
  validation, routing, evidence, and Gludd-created resources.
- Local operators control competing workloads, firmware, drivers, cabling, and
  host security. Successful discovery cannot prove exclusive use or healthy
  collectives.
- Runners and runtime projects control model/kernel support and scheduling.
  Gludd must pin and observe them; it cannot infer compatibility from accelerator
  kind alone.

## Exit criteria

A topic can move from `gap_open` only in a new reviewed ledger commit that names
an exact implementation SHA and exact candidate tuple; links focused hermetic,
security, privacy, ZDD, rollback, and live receipts; proves excluded-device and
fallback negatives; records cleanup; and passes coverage plus the full gate.
Documentation, branch-local tests, an upstream support table, device discovery,
a provider allocation, or one successful request cannot close a topic alone.
