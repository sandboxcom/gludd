## Scope and status

FreeLLMAPI v0.12.0 compatibility is not established. The release is a dated
upstream observation, not a Gludd candidate, dependency, or runtime admission.
The current v0.11.1 candidate is still pending its frozen delta, and the v0.9.9
derived scoring artifact remains disabled by default and shadow-only. An ABI-version match is necessary but not compatibility proof. The v0.1.2 sync
status is therefore `contract_only`; the full gate remains pending.

This contract covers discovery, verification, schema review, deterministic
generation, testing, promotion, and rollback. It does not authorize importing
the upstream server, MCP service, CLI, credential store, license-validation
network call, database, transports, provider execution, or lifecycle scripts.

## Immutable upstream identity

An upstream snapshot is one record, not a tag string. The candidate record must
contain all of the following before acquisition can affect generated output:

1. Canonical repository owner/name and stable repository identifier.
2. Release identifier, tag object identifier, tag name, publication timestamp,
   full commit hash, tree hash, and any signature payload and signer identity.
3. An exact verified archive digest acquired into a safe ephemeral directory;
   redirects, submodules, Git LFS objects, and archive membership are recorded.
4. Exact digests for the
   [`package-lock.json`](https://github.com/tashfeenahmed/freellmapi/blob/e4a47f203dba3b610dc180f628d3e821abbaf564/package-lock.json),
   [`LICENSE`](https://github.com/tashfeenahmed/freellmapi/blob/e4a47f203dba3b610dc180f628d3e821abbaf564/LICENSE),
   selected source paths, upstream test paths, and CI definition at
   [the exact commit](https://github.com/tashfeenahmed/freellmapi/blob/e4a47f203dba3b610dc180f628d3e821abbaf564/.github/workflows/ci.yml).
5. Gludd adapter version, compiler/bundler/runtime hashes, selected import graph,
   generated artifact digest, SBOM digest, and the admission receipt digest.

A mismatch, missing object, retag, unverifiable signature, extra archive member,
or repository transfer must fail closed. No runtime process downloads upstream
code or data.

## Ownership and allowed shim surface

No upstream source file or upstream test file may be copied into Gludd. Upstream
owns its catalog schema, model-configuration meaning, provider quirks, scoring
algorithms, server migrations, and tests. Gludd may neither fork those concepts
under new filenames nor edit a copied version to make a gate pass.

Gludd owns only the narrow integration seam: immutable candidate locking,
allowlisted import-graph selection, a versioned pure bridge ABI, bounded input
and output validation, a signed advisory-catalog adapter, deterministic artifact
generation, provenance receipts, and an atomic generation pointer. The allowed
stored upstream-derived surface is an attributed, digest-bound generated output
whose source graph and license are in its receipt. Provider calls, routing,
credentials, health, quotas, privacy, cost policy, scheduling, and failover stay
in Gludd.

The server, subprocess, sidecar, HTTP gateway, database, MCP endpoint, CLI, and
upstream credential lifecycle are outside the boundary. Any new import that
crosses that boundary invalidates the build rather than expanding ownership.

## Update and diff workflow

Each update is a new candidate and a replacement generation. It follows this
ordered, auditable workflow:

1. Discover release metadata without changing the candidate lock or runtime.
2. Resolve the complete identity tuple and acquire the exact verified archive
   into an isolated, size-bounded, non-executable workspace.
3. Verify repository/release/tag/commit relationships, signature policy, archive
   bytes and membership, license, package lock, and source-path digests.
4. Produce a mechanical old-to-new diff. Classify every change in selected paths
   and their import closure, catalog/model/config schemas, package and lock files,
   toolchain and test scripts, migrations, license, and security-sensitive code.
   An unclassified change stops the update.
5. Run upstream tests unmodified from that archive with its lockfile on every
   required, pinned toolchain. Record skipped, quarantined, networked, and
   platform-dependent cases; a skip is not a pass.
6. Exercise the schema/model-config migration contract side by side, including
   old, new, malformed, removed, renamed, and replayed fixtures.
7. Build the allowlisted pure artifact twice in clean environments. Require
   identical bytes, an identical import manifest, Node/QuickJS golden vectors,
   bridge ABI checks, license inventory, SBOM, and vulnerability evidence.
8. Freeze the behavior delta and run ablation, deterministic corpus, resource
   bound, malformed-input, and fallback tests. This creates evidence but does not
   admit the candidate.
9. Install a new named generation without overwriting the active one. Verify it
   with no traffic, then shadow it; canary requires explicit approval and live
   evidence. Promotion is a checked atomic pointer change.
10. Retain the prior generation and both receipts until the rollback window and
    evidence-retention policy expire.

The canonical current acquisition and matrix inputs are in the
[upstream build plan](../../config/freellmapi/upstream_build_plan.json). A release
that changes bootstrap, test, build, or migration scripts requires a reviewed
plan change before execution.

## Schema and model-config migration

Upstream schema and model-configuration semantics remain upstream-owned. Gludd
owns a bounded adapter, not a parallel schema. The adapter preserves the exact
signed catalog payload and version, identifies models by `(platform, model_id)`,
and maps only reviewed fields into advisory metadata; catalog rows never become
runnable provider identities.

For each candidate, produce old/new schema inventories and explicit transforms.
Renames and removals require tombstones; a removed model disables its generated
seed rather than falling through to an alias. New or unknown fields, enum values,
provider names, quota units, nullability, and default changes fail closed until
the adapter contract is reviewed. No best-effort coercion, silent field drop, or
implicit fallback is allowed.

Run forward, backward, replay, interrupted-update, and rollback checks on
synthetic or redacted immutable fixtures. Compare model identity, ordering,
defaults, constraint units, and signed-byte preservation. The upstream v0.12.0
request-history migration is a server database concern and is not ported or run
inside Gludd; its presence is nevertheless a mandatory delta-review signal. No
fixture may contain a real provider secret, prompt, response, or user identity.

## Upstream test execution and fixture reuse

The update workspace must run the root tests, migration round trips, lint, build,
and relevant coverage commands directly from the exact archive and pinned lock.
Upstream green is necessary but insufficient: Gludd separately proves selection,
bridge ABI, bounds, determinism, provenance, security, fallback, and rollback.

Tests remain in the verified ephemeral archive and are never imported into this
repository. Gludd may retain only data-only golden vectors or fixtures when each
entry records source release, full commit, original path, byte digest, license,
and transformation receipt. Such fixtures contain no executable test logic and
must be reproducible from the archive. Gludd-owned security and boundary tests
may consume those bytes without claiming ownership of upstream behavior.

## Supply-chain verification

**Source fact.** The exact upstream lockfile records dependency resolutions and
integrity data, while the root package declares install-script allowlisting. The
existing Gludd build plan uses `npm ci --no-audit --no-fund` on pinned Node 20 and
22 lanes.

**Gludd inference/requirement.** Lockfile integrity does not prove registry
provenance, and `--no-audit` is not a vulnerability audit. Admission therefore
requires a separate registry/provenance receipt, lifecycle-script and native
dependency inventory, offline or policy-controlled install evidence, complete
SBOM and license scan, vulnerability result with reviewed exceptions, two clean
reproducible builds, and keyless build provenance bound to the candidate record.

GitHub's verified-commit badge, a passing upstream CI workflow, npm integrity
fields, an archive checksum, and a Gludd signature each prove different facts;
none substitutes for the others. The receipt must state which verifier, trust
root, policy version, and timestamp established each fact. Secrets must not enter
build arguments, npm configuration captured in evidence, logs, fixtures, SBOMs,
or generated bundles.

## Security and privacy

The selected graph must be pure and network-free. It receives bounded primitive
input through the Gludd bridge and returns bounded primitive output; it receives
no prompt text, generated content, credentials, headers, cookies, filesystem
paths, environment, sockets, process APIs, or user identifiers. Execution keeps
the configured memory, time, stack, and output limits and falls back to Gludd's
native deterministic scorer on any validation, timeout, or runtime failure.

Catalog metadata is advisory and separately signed. Catalog reachability does
not grant provider credentials or demonstrate inference readiness. Provider
probes remain explicit, disabled, rate-limited, redacted, and Gludd-owned. The
license-validation call, key-management commands, analytics, MCP transport, and
all other upstream network paths stay excluded.

## ZDD and rollback

The active v0.9.9-derived artifact and last-known-good catalog remain available
throughout build and verification. A candidate is written to a new immutable,
named replacement generation; existing files and pointers are never edited in
place. Load and verify it before traffic, shadow against a fixed corpus, compare
bounded outputs and resource use, and canary only after its separate live-proof
gate is approved. Promotion atomically switches the checked generation pointer
and drains in-flight work under Gludd lifecycle control.

On any integrity, compatibility, latency, error-budget, privacy, catalog, or
provider-safety breach, atomically restore the prior pointer, disable the optional
feature, preserve both receipts and diagnostic evidence, and use the native
Gludd scorer and last-known-good signed catalog. Anti-rollback checks prevent an
unreviewed older catalog from being accepted during recovery. Rollback does not
delete provider-owned models, operator-owned configuration, credentials, or user
data, and it requires no upstream server or network access.

## Unresolved Node, npm, and live-provider constraints

Node 24, npm 11, and live-provider proof remain unresolved. Upstream's declared
Node range includes 24 and its npm lower bound permits later majors, but Gludd's
current build plan pins Node 20.20.2/npm 10.8.2 and Node 22.23.2/npm 10.9.8.
Neither package-engine metadata nor an upstream CI lane establishes behavior for
untested Gludd toolchains, native modules, lifecycle scripts, QuickJS output, or
the selected graph.

Live-provider behavior is provider-owned and time-varying. A catalog response,
upstream unit result, model row, or local mock cannot prove credentials, quota,
region, retirement state, request/response schema, streaming, pricing, safety,
or inference success. v0.12.0 therefore stays out of runtime admission until
explicit provider probes produce dated, redacted evidence under Gludd's policy;
missing credentials or unavailable providers remain pending rather than guessed.

## Exit criteria

v0.12.0 may move from observation to a candidate only after its full immutable
identity and archive receipt exist. Runtime admission additionally requires the
classified frozen delta, schema/model migration evidence, upstream and Gludd
test matrices, deterministic dual build, selected-graph proof, SBOM/license and
vulnerability evidence, signature/provenance verification, Node/QuickJS golden
vectors, bounds and fallback evidence, and successful ZDD rollback rehearsal.

Coverage thresholds are 85% aggregate and 75% per file for any code introduced
for an admitted adapter or generator, with no path exempted merely because it is
generated or provider-specific. Required live-provider lanes that cannot run are
marked pending. Until all mandatory receipts and the release gate are green, the
feature remains disabled by default, compatibility remains unestablished, and
the full gate remains pending.
