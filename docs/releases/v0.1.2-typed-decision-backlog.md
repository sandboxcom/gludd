# v0.1.2 Typed-Decision Backlog

**Release:** v0.1.2 or later
**Status:** Proposed, admission-gated, no production backend selected
**Decision record:**
[`Typed Decision Provider Admission`](../features/TYPED_DECISION_PROVIDER_ADMISSION.md)

## Outcome

This backlog turns the typed-decision research into five independently
deliverable core changes and five optional expansion artifacts. The release
objective is a provider-neutral, measurable, shadow-first decision layer for
one bounded Gludd task. It is not a commitment to ship OpenJev, Jev, or any
other upstream runtime.

The existing Gludd path remains authoritative until all five items pass their
own acceptance gates and an operator separately approves canary promotion. A
partially completed backlog must remain deployable: each item either has no
runtime effect or is dark/shadow-only by default.

## Fixed Candidate Boundaries

The following boundaries prevent the implementation from drifting into a
vendor-specific integration:

| Candidate | v0.1.2 boundary |
|---|---|
| TypeSafe Jev | Reference contract and optional evaluation backend only. No required account, credential, SDK, network test, or hosted dependency. A moving `jev-latest` alias cannot produce promotion evidence. |
| Laya | First preferred local shadow candidate after exact code, weight, tokenizer, renderer, calibration, and runtime pins exist. No direct import in task policy or business logic. |
| Verdict | Optional second evaluation candidate for calibrated abstention and risk/coverage comparison. Its native confidence or conformal set is evidence input, never Gludd authorization. |
| `razorback16/openjev` | May be exercised only as an externally managed Jev-shaped endpoint. Do not vendor its image, vLLM patch, model router, or daemon in this backlog. |
| Kev and LiteVar System One | Compatibility fixtures or optional externally managed endpoints only. No project-specific adapter. |
| Bespoke Nimble and other OpenJev-named repositories | Research and corpus comparison only. Their native schemas do not define Gludd's contract. |

Every backend must enter through the same protocol and identity types. Backend
names may appear in test fixtures, evaluation reports, or operator-supplied
profiles, but not in failure-classification policy branches.

## Global Non-Goals

- No typed-decision result authorizes command execution, repository mutation,
  credentials, networking, deployment, release, completion, or security action.
- No replacement of Gludd's current generative path, deterministic policy, or
  acceptance checks.
- No new provider preset: provider presets remain chat-completion integrations.
- No automatic model download, mutable model alias, unpinned container, or
  background daemon outside the universal model-worker lifecycle.
- No production use of upstream benchmark claims as Gludd capability evidence.
- No generic planning, prose generation, tool selection, or context compaction
  in this backlog. Context compaction requires a separate corpus and admission
  decision after failure classification succeeds.
- No live external service in required CI. All blocking tests are hermetic.

## TD12-01: Provider-Neutral Contract and Identity

### Deliverable

Add pure, dependency-free contracts for typed-decision requests, answers,
backend capabilities, and immutable backend identity. Add a transport protocol
interface plus fixture implementations; do not add a live client yet.

The identity fingerprint must bind at least:

- Gludd contract version;
- backend implementation and protocol version;
- endpoint trust class (`hosted_https` or `attested_local`), excluding secrets
  and mutable host content from telemetry;
- server code or container digest;
- model revision and model artifact digest;
- tokenizer digest;
- prompt renderer and scoring-contract digest;
- calibration artifact digest; and
- runtime version digest.

Request bounds must cover state bytes/tokens, question count, option count,
label and description length, and accepted question types. Response validation
must bind every answer to its request identifier and declared labels, require
finite values, reject duplicate/unknown answers, and preserve backend-native
probability and confidence semantics without translating them.

### Acceptance

- Unit tests cover every valid Choice, Score, and Noul shape and every bound.
- Mutation tests change each identity field independently; all changes produce
  a different fingerprint, while credentials and endpoint secrets never enter
  it.
- A compatibility fixture for each candidate class parses only through the
  generic contract. Backend-specific fields are retained as non-authoritative
  metadata or rejected; none changes normalized decision values silently.
- Malformed fixtures cover missing/extra question IDs, undeclared labels,
  non-finite values, out-of-range probabilities, bad sums beyond a documented
  rounding tolerance, invalid scores, oversized input, and unknown types. All
  fail closed with stable reason codes.
- New Python files have at least 85% aggregate and 75% per-file coverage; lint,
  strict type checking, warnings-as-errors tests, and the full gate pass.

### Non-Goals

No HTTP, SDK, model loading, threshold, routing, configuration, daemon, or
provider discovery is included. This item defines syntax and identity, not
semantic equivalence.

### ZDD and Rollback

The contracts are unreferenced by production wiring. Deploying or reverting
them changes no process, endpoint, stored record, or decision. Fixture schema
versions are additive; no migration exists.

## TD12-02: Frozen Calibration Corpus and Offline Harness

### Deliverable

Create a Gludd-owned failure-classification corpus, immutable manifest, and
offline evaluation harness. The corpus must use human-reviewed Gludd-shaped
failures rather than upstream demonstrations or model-generated labels alone.

Freeze at least 600 unique records:

- 300 calibration records and 300 held-out evaluation records;
- at least 50 held-out records in each required slice: option counts `2-4`,
  `5-10`, and `11+`; short and long state; explicit ambiguity/unknown; and
  adversarial or irrelevant instructions;
- every failure-taxonomy label represented by at least 20 held-out records, or
  the manifest must mark the label evaluation-only-ineligible; and
- no normalized state, source incident, or templated family may cross splits.

Each record includes source provenance, reviewer disposition, allowed labels,
an explicit `unknown`/abstain outcome where appropriate, sensitivity class, and
the exact request-schema version. Corpus publication requires two-person review
for ambiguous and high-impact examples. Sensitive raw logs stay outside Git;
tracked fixtures contain reviewed redactions only.

The harness must calculate accuracy, macro F1, per-label recall, Brier score,
expected calibration error with fixed bins, negative log loss, risk/coverage,
abstention rate, p50/p95 latency, throughput, and peak resident memory. It must
also run metamorphic checks for option order, label aliases, irrelevant state,
long-state boundaries, missing evidence, and adversarial instructions.

### Acceptance

- A deterministic manifest pins every fixture digest, split, source family,
  schema version, reviewer state, and license/provenance disposition.
- Re-running the hermetic reference fixture produces byte-identical metrics and
  ordering on supported Python versions.
- Automated checks reject duplicate/cross-split families, missing labels,
  unreviewed records, secrets, unsupported licenses, and post-freeze mutation.
- At least one deterministic baseline and two candidate-shaped fixture outputs
  exercise the entire report without downloading weights or calling a service.
- Reports clearly separate backend claims from measured Gludd results and bind
  every result to the TD12-01 identity fingerprint.
- Corpus and harness code meet the project coverage, lint, type, warning, and
  full-gate requirements.

### Non-Goals

The item does not choose a winner, fit a production threshold, call a live
candidate in required CI, or change a Gludd decision.

### ZDD and Rollback

Corpus and evaluation artifacts are read-only inputs with no daemon wiring.
Rollback removes the harness and its immutable fixtures together. Published
reports remain historical evidence and must not be silently regenerated under
the same manifest digest.

## TD12-03: Shadow-Only Failure Classification

### Deliverable

Implement one generic bounded transport and run typed decisions beside the
existing `failure_classification` path. The existing path returns the production
answer first; the shadow result is an evaluation receipt and has no execution
authority.

Only a Choice question over the existing failure taxonomy is in scope. The
transport accepts an operator-configured HTTPS endpoint or an endpoint already
attested and published by Gludd's model-worker lifecycle. It reuses canonical
URL/SSRF checks, disallows task-selected hosts and redirect trust changes,
retrieves credentials through the existing secret boundary, and applies exact
request, response, concurrency, queue, deadline, and retry bounds.

### Acceptance

- Tests prove shadow answers cannot alter the returned classification, retry,
  escalation, dispatch, or acceptance path under any response or exception.
- The primary path adds no network wait. At p95, queue/receipt bookkeeping adds
  no more than 5 ms and no more than 1 MiB steady-state memory per worker in the
  hermetic load test.
- A bounded queue rejects new shadow work when full; it never blocks the primary
  path, spawns replacement workers, or retries overload indefinitely.
- Timeout, 401, 403, 404, 422, 429, 529, 5xx, redirect, DNS change, malformed
  JSON, semantic mismatch, unknown model, and shutdown races all produce stable,
  redacted fallback reason codes and zero production divergence.
- Receipts bind request digest, identity fingerprint, primary and shadow label,
  latency, and disposition without logging state, criteria, tokens, endpoint,
  credential, or raw sensitive output.
- Startup, overload, drain, restart, and cancellation tests leave no owned task,
  socket, queue item, or process behind; project coverage and full gates pass.

### Non-Goals

No candidate is bundled or auto-started. No confidence threshold is used. No
shadow answer can replace, veto, retry, or delay the existing answer.

### ZDD and Rollback

The feature deploys disabled, then may be enabled in shadow mode without a
restart only after endpoint health and identity attestation. Disablement stops
new enqueues, drains or expires bounded in-flight shadow calls, and leaves the
primary path untouched. Receipts are append-only evidence and need no rollback
migration.

## TD12-04: Calibrated Abstention and Fail-Closed Fallback

### Deliverable

Fit and persist a Gludd-owned calibration and abstention policy for one exact
backend identity and the frozen TD12-02 corpus. The policy consumes raw
probabilities, never an upstream `confidence` field alone. It returns one of
`recommend`, `abstain`, or `invalid`; both latter outcomes use the current Gludd
path.

Calibration artifacts are keyed by identity, task, taxonomy version, option
count bucket, language/state slice, corpus manifest, method, and fit-tool
version. Any mismatch invalidates the artifact rather than borrowing a nearby
threshold.

### Acceptance

- Calibration uses only the calibration split; all promotion metrics use the
  untouched held-out split.
- Held-out expected calibration error is at most `0.05` overall and `0.10` for
  every eligible slice with at least 50 cases. Brier score must not regress from
  the uncalibrated candidate.
- A selected operating point must achieve at least `0.95` precision when it
  recommends, macro F1 no worse than `0.02` below the current path, and at least
  `0.20` coverage. Failure to meet all three keeps the backend shadow-only.
- On explicit ambiguity/unknown records, at least `0.90` abstain. On invalid,
  out-of-distribution, identity-mismatch, and missing-artifact fixtures, exactly
  `1.00` fall back to the current path.
- Option reorder and non-semantic label alias tests change recommendation rate
  by no more than two percentage points and never bypass abstention.
- Artifact serialization is deterministic, digest-bound, atomic, and rejected
  on partial write or version mismatch. Tests prove upstream confidence values
  cannot override the Gludd policy.

### Non-Goals

No online learning, self-calibration from production predictions, automatic
threshold promotion, security gate, or high-impact authorization is included.

### ZDD and Rollback

The calibrated policy remains advisory until TD12-05 promotes it. Removing or
invalidating the artifact causes immediate fallback, not process failure. A new
artifact is published beside the old one, switched atomically, and rolled back
by restoring the prior exact digest; in-flight calls retain the artifact they
started with.

## TD12-05: Drift, Canary, and Owned Lifecycle

### Deliverable

Add drift evaluation, explicit canary promotion, automatic demotion, and
complete endpoint lifecycle ownership. Only low-impact
`failure_classification` recommendations that TD12-04 would commit are eligible.

The rollout sequence is `shadow -> 1% -> 5% -> 25%`. Each stage requires a
minimum of 500 eligible decisions and 24 hours without a hard trigger before an
operator may promote. There is no automatic forward promotion. Automatic
demotion to shadow is required.

### Acceptance

- Compare a delayed human/accepted-outcome sample with the frozen baseline.
  Demote when rolling macro F1 drops more than `0.03`, ECE rises more than
  `0.02`, recommendation precision falls below `0.95`, or any eligible slice
  exceeds `0.10` Jensen-Shannon divergence for two consecutive windows.
- Immediately demote on identity/artifact mismatch, invalid response rate above
  `1%`, fallback rate above `10%` for five minutes, error rate above `2%` for
  five minutes, queue saturation above `5%` for five minutes, or any evidence
  that a typed decision influenced a forbidden impact.
- Demotion stops new canary decisions within 10 seconds and requires no restart.
  The existing path remains available throughout; in-flight candidate calls
  drain within their fixed deadline.
- Endpoint generations follow the universal lifecycle:
  `provision -> attest/configure -> health-ready -> publish -> work`, then
  `drain -> retire -> destroy -> absence proof`. Hosted endpoints implement the
  equivalent client/lease ownership without claiming remote infrastructure.
- Restart, blue/green replacement, endpoint loss, cache pressure, model update,
  artifact rollback, and process termination tests prove zero lost primary
  decisions and no orphaned process, port, cache lease, credential lease, or
  dispatch lease.
- Canary receipts and dashboards expose identity, stage, outcomes, drift,
  resource use, and demotion reason without task content or secrets. Coverage,
  warnings, security scans, and the full release gate pass.

### Non-Goals

No 100% rollout is authorized by this backlog. Expansion beyond 25%, adding a
second task, or allowing a self-hosted upstream image into Gludd's managed
runtime requires a new reviewed decision with fresh evaluation evidence.

### ZDD and Rollback

Every stage preserves the current path as the hot fallback. Candidate endpoint
generations publish only after health and identity attestation; the prior healthy
generation remains until the new generation completes its canary and all old
calls drain. Rollback first atomically selects shadow/current-path authority,
then drains, retires, destroys, and proves absence for Gludd-owned resources.
No database downgrade or receipt rewrite is allowed.

## TD12-06: Language/Domain-Aware Checkpoint Routing

### Deliverable and Candidate Boundary

Add a provider-neutral routing profile that selects an admitted immutable
identity before inference. The only routing inputs are the TD12-01 task and
schema versions, an operator-supplied language hint, a reviewed domain profile,
and capability evidence from TD12-02. Explicit trusted metadata takes priority;
content-derived detection may only recommend a route in shadow mode. Unknown,
mixed, or unsupported inputs use the generic candidate or current Gludd path.

The exact new boundary is a pure `RoutingProfile -> IdentityFingerprint`
decision plus a receipt. It cannot name a model in task policy, inspect
credentials, load weights, call a backend, or use a candidate's confidence to
route the request that produced that confidence. OpenJev routes and Laya
checkpoints are evaluation fixtures, not built-in profiles.

### Acceptance and Evaluation Metrics

- The frozen routing expansion set contains at least 100 held-out records for
  every eligible language/domain route and explicit mixed/unknown cases.
- Trusted explicit metadata is reproduced exactly. Unsupported, conflicting,
  or untrusted hints fall back in `100%` of held-out cases.
- Overall routed macro F1 is no more than `0.01` below the best eligible fixed
  candidate, and no eligible slice is more than `0.02` below its best
  predeclared candidate. Route-specific calibration must still pass TD12-04.
- Routing adds no more than 2 ms p95 locally, performs no network or model call,
  and emits no raw state, detected text, or secret in its receipt.
- Changing a route requires a new versioned profile digest. Reordering profiles
  or changing a backend alias cannot change the chosen immutable identity.

### Non-Goals

No universal language detector, automatic domain discovery, model-name branch,
online route learning, prompt inspection by an external service, or generic
task router is included. A route does not authorize execution or bypass the
universal task contract, calibration, abstention, or canary gates.

### ZDD and Rollback

Deploy profiles in shadow-recommendation mode and compare them with the fixed
route. Promotion atomically selects an exact profile digest while the prior
profile remains readable by in-flight work. Missing or invalid profiles select
the generic/current path. Rollback restores the previous digest without
restarting workers or changing stored receipts.

### Sources and Dated Caveat

- Laya's [router implementation](https://github.com/NandhaKishorM/laya/blob/main/laya/router.py)
  and [language detector](https://github.com/NandhaKishorM/laya/blob/main/laya/lang.py)
  demonstrate pre-inference checkpoint selection and its heuristic boundary.
- User reports [#35](https://github.com/NandhaKishorM/laya/issues/35),
  [#124](https://github.com/NandhaKishorM/laya/issues/124), and
  [#384](https://github.com/NandhaKishorM/laya/issues/384) show material
  per-language differences, confident errors, and silent misrouting of
  dictionary-shaped state.
- Reviewed 2026-09-27. These repositories and reports have a short public
  history; no long-lived production routing record was available. Gludd must
  therefore treat the behavior as a hypothesis to reproduce, not maturity
  evidence, and prefer explicit metadata over upstream heuristics.

## TD12-07: Schema-Grouped Bounded Batch Fan-Out

### Deliverable and Candidate Boundary

Add an optional scheduler that groups queued shadow requests only when all of
these keys match: immutable identity, task/schema version, question-schema
digest, token budget, calibration artifact, trust/sensitivity class, and
deadline bucket. It preserves request and question order, caps group size and
wait time, and fans a failed or unsupported batch back out to bounded individual
calls without extending the original deadlines.

The exact boundary is a transport-level `BatchPlan`; callers and task policy
still observe one TD12-01 request and response at a time. No backend-specific
batch shape escapes the adapter. Cross-tenant or cross-sensitivity grouping is
forbidden even when it would improve throughput.

### Acceptance and Evaluation Metrics

- For the frozen corpus, normalized IDs, ordering, answers, and fallback reason
  codes match sequential execution exactly. Raw numeric differences must stay
  within a declared `1e-5` tolerance; any threshold crossing abstains.
- On a recorded production-shaped load fixture, batching either doubles
  throughput or reduces candidate compute time by at least `30%`, while p95
  end-to-end latency regresses by no more than `10%` and deadline misses by no
  more than one percentage point.
- Peak memory stays within the TD12-08 budget. Queue, cancellation, partial
  response, overload, and shutdown tests leave zero unresolved requests.
- Property tests permute arrival and schema order and prove no result is bound
  to another request, identity, calibration artifact, or sensitivity class.
- If the benefit target is missed, the scheduler remains disabled; semantics
  or isolation may not be relaxed to manufacture a throughput win.

### Non-Goals

No unbounded queue, dynamic semantic coalescing, cross-trust batching, changed
question meaning, backend-native response leakage, or assumption that every
provider supports batching is included. Sorting by length is optional and must
not change Gludd's normalized decision.

### ZDD and Rollback

Ship disabled, then mirror batch plans without sending them. Enable per exact
identity with a bounded percentage. Disablement stops new groups, lets accepted
groups drain within their deadlines, and sends later requests individually.
Rollback changes no request schema, calibration artifact, or primary path.

### Sources and Dated Caveat

- Laya documents [schema-grouped heterogeneous routing and bounded batching](https://github.com/NandhaKishorM/laya/blob/main/laya/router.py)
  and its [throughput/memory trade-offs](https://github.com/NandhaKishorM/laya/blob/main/README.md).
- OpenJev's [README](https://github.com/razorback16/openjev/blob/main/README.md)
  exposes encoder batch sizing and multi-question request behavior, but those
  are implementation observations rather than a Gludd contract.
- Reviewed 2026-09-27. Upstream throughput figures are hardware-specific and
  the projects lack long-lived user reports about batch isolation. Gludd accepts
  only reproduced workload metrics and exact isolation tests.

## TD12-08: Memory-Budgeted Preload and Eviction

### Deliverable and Candidate Boundary

Add an operator-owned residency policy for admitted local identities. The
policy computes a preload/eviction plan from declared artifact size, measured
resident memory, device headroom, current leases, route demand, and cold-start
cost. It may preload only exact admitted identities and evict only idle,
unleased generations. Downloads remain a separate explicit lifecycle action.

The exact boundary is the universal model-worker's existing
`provision -> publish -> lease -> drain -> retire -> destroy` lifecycle plus a
versioned `ResidencyPlan`. It does not call framework garbage collection,
CUDA-specific cache APIs, or a candidate router directly. Local, hosted, CPU,
GPU, and future runtimes expose the same opaque capacity and lease facts.

### Acceptance and Evaluation Metrics

- Stress tests stay below the configured resident cap and below `90%` of
  measured device capacity, with zero out-of-memory events or orphaned
  generations through preload, eviction, cancellation, and restart.
- No identity is loaded twice, no leased/in-flight generation is evicted, and
  every retired generation reaches absence proof in `100%` of fault-injection
  cases.
- For an approved hot set, preload reduces p95 first-decision latency by at
  least `40%` without increasing p95 steady-state latency by more than `5%`.
- A missing, stale, or infeasible plan degrades to on-demand lifecycle behavior.
  The planner never raises a memory limit or downloads an artifact.
- Receipts expose planned versus measured bytes, lease count, reason, and exact
  identity without task content or host-global process details.

### Non-Goals

No candidate-specific cache cleaner, implicit download, forced eviction,
host-wide memory manager, overcommit, or bypass of lifecycle ownership is
included. Upstream footprint estimates do not substitute for Gludd measurement.

### ZDD and Rollback

Run the planner in advisory mode first. A promoted plan preloads a new healthy
generation before publishing it and drains old generations only after leases
finish. Disabling the plan stops new preloads and returns to on-demand loading;
rollback never kills an in-flight worker or invalidates the hot fallback.

### Sources and Dated Caveat

- Laya's [router source](https://github.com/NandhaKishorM/laya/blob/main/laya/router.py)
  provides preload, bounded loaded-model count, and idle LRU eviction as a
  useful reference, while exposing framework-specific cleanup Gludd must not
  copy into policy.
- OpenJev's [documented resource footprints and routed-container behavior](https://github.com/razorback16/openjev/blob/main/README.md)
  show why listing a model is not proof it is resident or ready.
- Reviewed 2026-09-27. Reported memory sizes vary by accelerator, runtime, and
  model revision, and there is no long-lived public operational history.
  Admission depends on Gludd-measured bytes and lifecycle fault tests.

## TD12-09: Redaction and Injection-Safe Observer Stages

### Deliverable and Candidate Boundary

Add two narrow, provider-neutral stages around hosted shadow transport: a pure
pre-transport sanitizer that returns a copied request plus a redaction receipt,
and a post-response observer that receives an immutable normalized result.
Sanitizer rules are operator-owned, versioned, deterministic, and evaluated on
the frozen corpus. An untrusted task, state, response, or backend cannot install
a stage or modify routing, token limits, identity, calibration, or authority.

The exact extension points are `Sanitizer.sanitize(request) ->
(request, receipt)` and `Observer.observe(read_only_result) -> None`. There is
no arbitrary callback, dynamic code import, external forwarding, result
replacement, or exception path that can turn a shadow prediction into action.

### Acceptance and Evaluation Metrics

- The secret/redaction fixture covers every supported credential and personal
  data class. Seeded secrets are removed before hosted transport in `100%` of
  cases, with false redaction below `1%` on reviewed safe tokens.
- Sanitization reduces held-out macro F1 by no more than `0.01`, adds at most
  5 ms p95, and produces receipts containing rule/digest/counts but no original
  or replacement content.
- Mutation, fuzz, and adversarial-instruction tests prove observers cannot
  change requests, results, routes, thresholds, fallback, logs, or execution.
- Sanitizer timeout, exception, unknown rule version, or incomplete redaction
  falls back to the current path and sends zero bytes to the hosted endpoint.
- Attested local endpoints may use an explicit no-redaction profile, but it has
  its own digest and cannot be selected by task content.

### Non-Goals

No general plugin API, prompt injection defense claim, output rewriting,
user-authored callback, third-party telemetry forwarding, or automatic cache is
included. Redaction does not make an untrusted endpoint trusted and cannot
weaken SSRF, secret, or data-classification policy.

### ZDD and Rollback

Deploy observers read-only and sanitizers in audit comparison before enabling
hosted sends. Promotion is atomic per exact sanitizer digest. Missing or failed
sanitization fails closed to the current path, never to unredacted transport.
Rollback selects the prior digest or disables hosted shadowing; local primary
decisions remain hot and unchanged.

### Sources and Dated Caveat

- Laya's [hook implementation](https://github.com/NandhaKishorM/laya/blob/main/laya/router.py)
  permits request replacement, result replacement, routing override, and
  external forwarding. It motivates the use case and the stricter Gludd
  boundary; it is not an API to copy.
- The Laya [README hook examples](https://github.com/NandhaKishorM/laya/blob/main/README.md)
  cover audit, PII redaction, caching, metrics, and confidence gating.
- Reviewed 2026-09-27. No long-lived public security review of these hooks was
  available. Until Gludd's adversarial and data-loss fixtures pass, arbitrary
  mutation/injection remains explicitly rejected.

## TD12-10: Domain-Adaptation Admission

### Deliverable and Candidate Boundary

Add an offline admission path for a domain-adapted full or adapter checkpoint
only after an admitted base candidate misses a predeclared TD12-02
discrimination target and TD12-04 calibration cannot repair its ranking.
Training data needs source-family separation, license/provenance approval,
reviewed labels, sensitivity disposition, and a frozen recipe. The adapted
artifact always receives a new TD12-01 identity and repeats calibration,
abstention, routing, drift, and canary evaluation from zero.

The exact runtime boundary is an `AdaptedArtifactManifest` containing base
identity, weight/adapter digest, tokenizer/renderer digests, corpus and recipe
digests, license disposition, and evaluation report. Training remains an
offline external operation; Gludd runtime only admits or rejects immutable
artifacts through the universal model-worker interface.

### Acceptance and Evaluation Metrics

- On untouched domain-held-out data, macro F1 improves by at least `0.05` over
  the same routed base candidate, and no eligible non-domain or language slice
  regresses by more than `0.02`.
- After fresh TD12-04 calibration, overall ECE is at most `0.05`, every eligible
  slice is at most `0.10`, and recommendation precision remains at least
  `0.95`; otherwise the artifact stays offline.
- Three seeded training/evaluation reproductions vary by no more than `0.01`
  macro F1 and bind byte-identical input manifests. Weight bytes may differ
  only where the manifest documents nondeterminism and exact output digests.
- Automated checks reject cross-split source families, production secrets,
  model-generated labels without review, incompatible licenses, mutable bases,
  and any attempt to replace an existing identity in place.
- The evaluation report separates representation improvement from calibration
  improvement and compares against deterministic and current-path baselines.

### Non-Goals

No online/self-training, production-log harvesting, provider-specific trainer,
continuous weight mutation, calibration disguised as fine-tuning, or automatic
promotion is included. Domain adaptation cannot narrow Gludd's universal task
schema or create domain-specific authorization logic.

### ZDD and Rollback

Publish an adapted artifact beside its base, then evaluate it offline and in
shadow under a new identity. Canary promotion follows TD12-05 with the base and
current path still hot. Rollback atomically selects the prior identity, drains
the adapted generation, retires/destroys owned resources, and retains immutable
evidence; no in-place weight or database rollback exists.

## Release Evidence

Completing any item requires one atomic feature branch commit, focused tests,
warning-free lint and type checks, coverage of at least 85% aggregate and 75%
per changed file, and the full project gate. Completion evidence must name the
exact commit, identity/schema version, tests, coverage, and rollback exercise.

The core backlog is not complete until TD12-01 through TD12-05 are delivered in
dependency order, TD12-05 remains capped at 25%, and the admission decision is
re-reviewed against the then-current upstream lifecycle and practitioner
evidence. TD12-06 through TD12-10 are independently admissible expansion items;
an unfinished or rejected expansion does not block the core release. A backend
that misses a quality gate remains a valid shadow research backend; the release
must not weaken a metric to force promotion.
