# v0.1.2 Typed-Decision Backlog

**Release:** v0.1.2 or later
**Status:** Proposed, admission-gated, no production backend selected
**Decision record:**
[`Typed Decision Provider Admission`](../features/TYPED_DECISION_PROVIDER_ADMISSION.md)

## Outcome

This backlog turns the typed-decision research into five independently
deliverable changes. The release objective is a provider-neutral, measurable,
shadow-first decision layer for one bounded Gludd task. It is not a commitment
to ship OpenJev, Jev, or any other upstream runtime.

The existing Gludd path remains authoritative until all five items pass their
own acceptance gates and an operator separately approves canary promotion. A
partially completed backlog must remain deployable: each item either has no
runtime effect or is dark/shadow-only by default.

## Fixed Candidate Boundaries

The following boundaries prevent the implementation from drifting into a
vendor-specific integration:

| Candidate | v0.1.2 boundary |
|---|---|
| TypeSafe Jev | Reference contract and optional evaluation backend only. No required account, credential, SDK, network test, or hosted dependency. A moving `jev-latest` alias cannot produce promotion evidence. |
| Laya | First preferred local shadow candidate after exact code, weight, tokenizer, renderer, calibration, and runtime pins exist. No direct import in task policy or business logic. |
| Verdict | Optional second evaluation candidate for calibrated abstention and risk/coverage comparison. Its native confidence or conformal set is evidence input, never Gludd authorization. |
| `razorback16/openjev` | May be exercised only as an externally managed Jev-shaped endpoint. Do not vendor its image, vLLM patch, model router, or daemon in this backlog. |
| Kev and LiteVar System One | Compatibility fixtures or optional externally managed endpoints only. No project-specific adapter. |
| Bespoke Nimble and other OpenJev-named repositories | Research and corpus comparison only. Their native schemas do not define Gludd's contract. |

Every backend must enter through the same protocol and identity types. Backend
names may appear in test fixtures, evaluation reports, or operator-supplied
profiles, but not in failure-classification policy branches.

## Global Non-Goals

- No typed-decision result authorizes command execution, repository mutation,
  credentials, networking, deployment, release, completion, or security action.
- No replacement of Gludd's current generative path, deterministic policy, or
  acceptance checks.
- No new provider preset: provider presets remain chat-completion integrations.
- No automatic model download, mutable model alias, unpinned container, or
  background daemon outside the universal model-worker lifecycle.
- No production use of upstream benchmark claims as Gludd capability evidence.
- No generic planning, prose generation, tool selection, or context compaction
  in this backlog. Context compaction requires a separate corpus and admission
  decision after failure classification succeeds.
- No live external service in required CI. All blocking tests are hermetic.

## TD12-01: Provider-Neutral Contract and Identity

### Deliverable

Add pure, dependency-free contracts for typed-decision requests, answers,
backend capabilities, and immutable backend identity. Add a transport protocol
interface plus fixture implementations; do not add a live client yet.

The identity fingerprint must bind at least:

- Gludd contract version;
- backend implementation and protocol version;
- endpoint trust class (`hosted_https` or `attested_local`), excluding secrets
  and mutable host content from telemetry;
- server code or container digest;
- model revision and model artifact digest;
- tokenizer digest;
- prompt renderer and scoring-contract digest;
- calibration artifact digest; and
- runtime version digest.

Request bounds must cover state bytes/tokens, question count, option count,
label and description length, and accepted question types. Response validation
must bind every answer to its request identifier and declared labels, require
finite values, reject duplicate/unknown answers, and preserve backend-native
probability and confidence semantics without translating them.

### Acceptance

- Unit tests cover every valid Choice, Score, and Noul shape and every bound.
- Mutation tests change each identity field independently; all changes produce
  a different fingerprint, while credentials and endpoint secrets never enter
  it.
- A compatibility fixture for each candidate class parses only through the
  generic contract. Backend-specific fields are retained as non-authoritative
  metadata or rejected; none changes normalized decision values silently.
- Malformed fixtures cover missing/extra question IDs, undeclared labels,
  non-finite values, out-of-range probabilities, bad sums beyond a documented
  rounding tolerance, invalid scores, oversized input, and unknown types. All
  fail closed with stable reason codes.
- New Python files have at least 85% aggregate and 75% per-file coverage; lint,
  strict type checking, warnings-as-errors tests, and the full gate pass.

### Non-Goals

No HTTP, SDK, model loading, threshold, routing, configuration, daemon, or
provider discovery is included. This item defines syntax and identity, not
semantic equivalence.

### ZDD and Rollback

The contracts are unreferenced by production wiring. Deploying or reverting
them changes no process, endpoint, stored record, or decision. Fixture schema
versions are additive; no migration exists.

## TD12-02: Frozen Calibration Corpus and Offline Harness

### Deliverable

Create a Gludd-owned failure-classification corpus, immutable manifest, and
offline evaluation harness. The corpus must use human-reviewed Gludd-shaped
failures rather than upstream demonstrations or model-generated labels alone.

Freeze at least 600 unique records:

- 300 calibration records and 300 held-out evaluation records;
- at least 50 held-out records in each required slice: option counts `2-4`,
  `5-10`, and `11+`; short and long state; explicit ambiguity/unknown; and
  adversarial or irrelevant instructions;
- every failure-taxonomy label represented by at least 20 held-out records, or
  the manifest must mark the label evaluation-only-ineligible; and
- no normalized state, source incident, or templated family may cross splits.

Each record includes source provenance, reviewer disposition, allowed labels,
an explicit `unknown`/abstain outcome where appropriate, sensitivity class, and
the exact request-schema version. Corpus publication requires two-person review
for ambiguous and high-impact examples. Sensitive raw logs stay outside Git;
tracked fixtures contain reviewed redactions only.

The harness must calculate accuracy, macro F1, per-label recall, Brier score,
expected calibration error with fixed bins, negative log loss, risk/coverage,
abstention rate, p50/p95 latency, throughput, and peak resident memory. It must
also run metamorphic checks for option order, label aliases, irrelevant state,
long-state boundaries, missing evidence, and adversarial instructions.

### Acceptance

- A deterministic manifest pins every fixture digest, split, source family,
  schema version, reviewer state, and license/provenance disposition.
- Re-running the hermetic reference fixture produces byte-identical metrics and
  ordering on supported Python versions.
- Automated checks reject duplicate/cross-split families, missing labels,
  unreviewed records, secrets, unsupported licenses, and post-freeze mutation.
- At least one deterministic baseline and two candidate-shaped fixture outputs
  exercise the entire report without downloading weights or calling a service.
- Reports clearly separate backend claims from measured Gludd results and bind
  every result to the TD12-01 identity fingerprint.
- Corpus and harness code meet the project coverage, lint, type, warning, and
  full-gate requirements.

### Non-Goals

The item does not choose a winner, fit a production threshold, call a live
candidate in required CI, or change a Gludd decision.

### ZDD and Rollback

Corpus and evaluation artifacts are read-only inputs with no daemon wiring.
Rollback removes the harness and its immutable fixtures together. Published
reports remain historical evidence and must not be silently regenerated under
the same manifest digest.

## TD12-03: Shadow-Only Failure Classification

### Deliverable

Implement one generic bounded transport and run typed decisions beside the
existing `failure_classification` path. The existing path returns the production
answer first; the shadow result is an evaluation receipt and has no execution
authority.

Only a Choice question over the existing failure taxonomy is in scope. The
transport accepts an operator-configured HTTPS endpoint or an endpoint already
attested and published by Gludd's model-worker lifecycle. It reuses canonical
URL/SSRF checks, disallows task-selected hosts and redirect trust changes,
retrieves credentials through the existing secret boundary, and applies exact
request, response, concurrency, queue, deadline, and retry bounds.

### Acceptance

- Tests prove shadow answers cannot alter the returned classification, retry,
  escalation, dispatch, or acceptance path under any response or exception.
- The primary path adds no network wait. At p95, queue/receipt bookkeeping adds
  no more than 5 ms and no more than 1 MiB steady-state memory per worker in the
  hermetic load test.
- A bounded queue rejects new shadow work when full; it never blocks the primary
  path, spawns replacement workers, or retries overload indefinitely.
- Timeout, 401, 403, 404, 422, 429, 529, 5xx, redirect, DNS change, malformed
  JSON, semantic mismatch, unknown model, and shutdown races all produce stable,
  redacted fallback reason codes and zero production divergence.
- Receipts bind request digest, identity fingerprint, primary and shadow label,
  latency, and disposition without logging state, criteria, tokens, endpoint,
  credential, or raw sensitive output.
- Startup, overload, drain, restart, and cancellation tests leave no owned task,
  socket, queue item, or process behind; project coverage and full gates pass.

### Non-Goals

No candidate is bundled or auto-started. No confidence threshold is used. No
shadow answer can replace, veto, retry, or delay the existing answer.

### ZDD and Rollback

The feature deploys disabled, then may be enabled in shadow mode without a
restart only after endpoint health and identity attestation. Disablement stops
new enqueues, drains or expires bounded in-flight shadow calls, and leaves the
primary path untouched. Receipts are append-only evidence and need no rollback
migration.

## TD12-04: Calibrated Abstention and Fail-Closed Fallback

### Deliverable

Fit and persist a Gludd-owned calibration and abstention policy for one exact
backend identity and the frozen TD12-02 corpus. The policy consumes raw
probabilities, never an upstream `confidence` field alone. It returns one of
`recommend`, `abstain`, or `invalid`; both latter outcomes use the current Gludd
path.

Calibration artifacts are keyed by identity, task, taxonomy version, option
count bucket, language/state slice, corpus manifest, method, and fit-tool
version. Any mismatch invalidates the artifact rather than borrowing a nearby
threshold.

### Acceptance

- Calibration uses only the calibration split; all promotion metrics use the
  untouched held-out split.
- Held-out expected calibration error is at most `0.05` overall and `0.10` for
  every eligible slice with at least 50 cases. Brier score must not regress from
  the uncalibrated candidate.
- A selected operating point must achieve at least `0.95` precision when it
  recommends, macro F1 no worse than `0.02` below the current path, and at least
  `0.20` coverage. Failure to meet all three keeps the backend shadow-only.
- On explicit ambiguity/unknown records, at least `0.90` abstain. On invalid,
  out-of-distribution, identity-mismatch, and missing-artifact fixtures, exactly
  `1.00` fall back to the current path.
- Option reorder and non-semantic label alias tests change recommendation rate
  by no more than two percentage points and never bypass abstention.
- Artifact serialization is deterministic, digest-bound, atomic, and rejected
  on partial write or version mismatch. Tests prove upstream confidence values
  cannot override the Gludd policy.

### Non-Goals

No online learning, self-calibration from production predictions, automatic
threshold promotion, security gate, or high-impact authorization is included.

### ZDD and Rollback

The calibrated policy remains advisory until TD12-05 promotes it. Removing or
invalidating the artifact causes immediate fallback, not process failure. A new
artifact is published beside the old one, switched atomically, and rolled back
by restoring the prior exact digest; in-flight calls retain the artifact they
started with.

## TD12-05: Drift, Canary, and Owned Lifecycle

### Deliverable

Add drift evaluation, explicit canary promotion, automatic demotion, and
complete endpoint lifecycle ownership. Only low-impact
`failure_classification` recommendations that TD12-04 would commit are eligible.

The rollout sequence is `shadow -> 1% -> 5% -> 25%`. Each stage requires a
minimum of 500 eligible decisions and 24 hours without a hard trigger before an
operator may promote. There is no automatic forward promotion. Automatic
demotion to shadow is required.

### Acceptance

- Compare a delayed human/accepted-outcome sample with the frozen baseline.
  Demote when rolling macro F1 drops more than `0.03`, ECE rises more than
  `0.02`, recommendation precision falls below `0.95`, or any eligible slice
  exceeds `0.10` Jensen-Shannon divergence for two consecutive windows.
- Immediately demote on identity/artifact mismatch, invalid response rate above
  `1%`, fallback rate above `10%` for five minutes, error rate above `2%` for
  five minutes, queue saturation above `5%` for five minutes, or any evidence
  that a typed decision influenced a forbidden impact.
- Demotion stops new canary decisions within 10 seconds and requires no restart.
  The existing path remains available throughout; in-flight candidate calls
  drain within their fixed deadline.
- Endpoint generations follow the universal lifecycle:
  `provision -> attest/configure -> health-ready -> publish -> work`, then
  `drain -> retire -> destroy -> absence proof`. Hosted endpoints implement the
  equivalent client/lease ownership without claiming remote infrastructure.
- Restart, blue/green replacement, endpoint loss, cache pressure, model update,
  artifact rollback, and process termination tests prove zero lost primary
  decisions and no orphaned process, port, cache lease, credential lease, or
  dispatch lease.
- Canary receipts and dashboards expose identity, stage, outcomes, drift,
  resource use, and demotion reason without task content or secrets. Coverage,
  warnings, security scans, and the full release gate pass.

### Non-Goals

No 100% rollout is authorized by this backlog. Expansion beyond 25%, adding a
second task, or allowing a self-hosted upstream image into Gludd's managed
runtime requires a new reviewed decision with fresh evaluation evidence.

### ZDD and Rollback

Every stage preserves the current path as the hot fallback. Candidate endpoint
generations publish only after health and identity attestation; the prior healthy
generation remains until the new generation completes its canary and all old
calls drain. Rollback first atomically selects shadow/current-path authority,
then drains, retires, destroys, and proves absence for Gludd-owned resources.
No database downgrade or receipt rewrite is allowed.

## Release Evidence

Completing any item requires one atomic feature branch commit, focused tests,
warning-free lint and type checks, coverage of at least 85% aggregate and 75%
per changed file, and the full project gate. Completion evidence must name the
exact commit, identity/schema version, tests, coverage, and rollback exercise.

The backlog as a whole is not complete until all five items are delivered in
dependency order, TD12-05 remains capped at 25%, and the admission decision is
re-reviewed against the then-current upstream lifecycle and practitioner
evidence. A backend that misses a quality gate remains a valid shadow research
backend; the release must not weaken a metric to force promotion.
