# v0.1.2 Azure accelerator acceptance design

Status: implementation-ready design; no accelerator capability is admitted by
this document  
Design base: `dcd27ffdd9425eb5ff80e1d037b0e6066dccb017`  
Reviewed: 2026-09-28  
Release: v0.1.2

## Decision

Gludd may advertise an Azure accelerator route only after one exact candidate
has passed the admission state machine in this document and its evidence bundle
has passed offline verification. An inventory result, quota approval, successful
VM allocation, runner health response, or locally generated request is not by
itself acceptance evidence.

The first admissible production shapes are:

1. one Azure GPU Virtual Machine (VM) running one pinned vLLM release;
2. one Azure GPU VM using host-local tensor or pipeline parallelism with an
   attested device topology and a pinned vLLM release;
3. one Azure GPU VM running one pinned Ollama release, with requested device
   visibility and observed model placement recorded separately; and
4. a remote Gludd consumer reaching any admitted shape through the stable model
   gateway profile, never through a raw runner or VM endpoint.

Azure Container Apps GPU workload profiles, multi-host vLLM, and Google Cloud
TPU are separate acceptance tracks. They cannot inherit an Azure VM result.
TPU remains contract-only in v0.1.2 unless a later release supplies a dedicated,
provider-specific live proof.

## Terms and provider boundaries

| Term | Meaning in this design | Forbidden inference |
|---|---|---|
| Azure VM | A virtual machine supplied by Microsoft Azure Compute. A VM Scale Set (VMSS) is the Azure group primitive. | “Azure EC2” is not a product or accepted synonym. |
| Amazon EC2 | Amazon Elastic Compute Cloud, the AWS virtual-server service. | An EC2 test says nothing about Azure allocation or topology. |
| Azure Container Apps GPU | A managed Container Apps workload profile with its own GPU, quota, driver, and scheduling boundaries. | It is not an Azure GPU VM and does not prove multi-GPU. |
| GPU device | A guest-visible accelerator identified by stable UUID plus PCI/topology facts. | A requested count does not prove visibility, health, or use. |
| Google Cloud TPU | A Google Cloud TPU VM and slice/topology lifecycle using a TPU-specific runtime. | TPU is not available as an Azure VM accelerator and is not a GPU backend. |
| runner | The exact vLLM or Ollama build that loads a model. | A runner tag without its resolved commit and artifact digest is not immutable. |
| remote consumer | A workload outside the accelerator guest that calls a Gludd logical profile through the gateway. | A request generated on the VM is not a remote-consumption proof. |

Microsoft calls this service [Azure Virtual Machines][azure-vm-overview]. AWS
calls its service [Amazon EC2][aws-ec2]. Code, UI, documentation, evidence, and
operator messages must preserve that distinction.

## Acceptance object

Implementation must introduce an immutable `AcceleratorAcceptanceCandidate`.
The serialized object is the admission input and the root of the evidence
manifest. It contains, at minimum:

```text
candidate_id
design_base_commit
gludd_commit
provider + subscription_tenant_fingerprint
region + availability_zone
resource_group_id + vm_resource_id
azure_vm_size + reported_sku_capabilities
os_image_publisher/offer/sku/version + image_digest_or_version_id
guest_kernel + accelerator_driver + firmware + CUDA/ROCm versions
runner_name + runner_release + runner_source_commit + runner_artifact_digest
model_repository + model_revision + weights/config/tokenizer digests
model_architecture + parameter_count + quantization + dtype
requested_context_tokens + concurrent_sequences + batch/token-rate envelope
device UUIDs + PCI addresses + NUMA nodes + memory + health
NVLink/NVSwitch/RDMA/P2P topology and collective probe result
tensor/pipeline/data parallel degrees and rank-to-device mapping
logical_profile + gateway_generation + runner_generation
source_snapshot_receipt_ids
lease_id + creation/expiry timestamps
```

Cloud subscription and tenant identifiers are stored only as keyed
fingerprints. The public manifest must not contain credentials, bearer tokens,
private keys, raw prompts, generated content, public IP addresses, or unredacted
customer/resource names.

Every mutable input also has a `SourceSnapshotReceipt`:

```json
{
  "source_uri": "https://example.invalid/source",
  "source_kind": "official_doc|api_response|release|model_artifact|issue",
  "version_or_api_version": "exact value",
  "resolved_commit": "full commit when applicable",
  "artifact_digest": "sha256:... when applicable",
  "retrieved_at": "RFC3339 timestamp",
  "body_sha256": "sha256 of canonical bytes",
  "provenance": "publisher and license metadata",
  "admission_role": "normative|regression_input|informational"
}
```

A mutable web page may create an informational or regression receipt, but it
cannot be the sole normative basis for promotion. Release tags must be resolved
to full commits; container tags must be resolved to OCI digests; model aliases
must be resolved to immutable revisions and per-file hashes.

## Admission state machine

```text
DISCOVERED
  -> SIZED
  -> PREFLIGHTED
  -> ALLOCATED
  -> GUEST_ATTESTED
  -> RUNNER_READY
  -> REMOTE_PROVED
  -> CANARY
  -> PROMOTED
  -> DRAINED
  -> CLEANUP_VERIFIED
```

Each transition writes a signed phase receipt before the next begins. A
pre-allocation failure becomes `REFUSED`; a post-allocation failure becomes
`ROLLBACK_REQUIRED`. No failure may silently select another SKU, region, model,
quantization, context length, runner, or device count.

The implementation must be resumable and idempotent by `candidate_id` and
`lease_id`. A retry may continue an exact candidate only when the preceding
receipt still verifies and its observation TTL has not expired. Otherwise a new
candidate and generation are required.

## Azure availability admission

Azure exposes four distinct facts. They are not interchangeable:

1. **catalog visibility**: the [Resource SKUs API][azure-resource-skus] reports the exact VM size in
   the requested region/zone, including capabilities and restrictions;
2. **quota headroom**: both [total regional vCPU quota and the VM-family quota][azure-quota]
   cover the requested generation;
3. **capacity observation**: a fresh provider response reports a finite result
   for the exact size/location/zone, when that API is available; and
4. **allocation**: Azure successfully creates the exact leased VM and its
   observed identity matches the candidate.

Quota is an authorization ceiling, not capacity. [Azure documents][azure-allocation-failure] that an
allocation can still fail with `AllocationFailed` or `ZonalAllocationFailed`
after quota approval. Therefore:

- `PREFLIGHTED` requires catalog, both quota checks, price/budget evidence, and
  non-expired capacity evidence or an explicit `capacity_unknown` result;
- `capacity_unknown` may attempt a bounded allocation but cannot become a pass;
- `ALLOCATED` requires the exact SKU, region, zone, image, device count, lease,
  and resource IDs from the provider response;
- a provider substitution is a refusal, not a successful fallback; and
- a resize is never used for zero-downtime replacement because [Azure documents][azure-resize]
  restart/deallocation cases during resize.

The implementation must distinguish absence (`not listed`), restriction,
quota exhaustion, capacity exhaustion, provider throttling, and authentication
failure. Each has a stable machine code and preserves the redacted provider
request/correlation ID.

## Model right-sizing admission

Static sizing is a preflight estimate, not live capacity proof. The candidate
must record the input evidence and reproduce this calculation:

```text
runtime_and_kv = runtime_overhead_bytes
               + kv_bytes_per_token * context_tokens * concurrent_sequences

per_device_required = ceil(weight_bytes / model_parallel_devices)
                    + runtime_and_kv

usable_device_memory = device_memory_bytes
                     * (1000 - reserve_millis) / 1000
```

`weight_bytes`, runtime overhead, and KV cost come from the exact model and
runner revision, not the model's marketing name. Admission also requires a
bounded live calibration at the requested context, concurrency, batch, token
rate, and streaming behavior. It records peak device memory, host memory,
latency percentiles, throughput, queue depth, and out-of-memory results.

Selection follows these rules:

1. choose the least costly single-device candidate that fits and meets the
   service-level objective;
2. use multiple devices only when a single device cannot meet capacity/SLO, or
   a measured Pareto improvement justifies the added failure surface;
3. preserve the requested model revision, quantization, dtype, context, and
   quality contract—automatic quantization or context reduction is forbidden;
4. reject a candidate whose live high-water mark crosses its reserve; and
5. re-run sizing when any model, runner, driver, device, topology, workload, or
   reserve input changes.

This least-device policy is deliberate: practitioner reports show cases where
Ollama became slower after spreading a model that fit on one GPU.

## Multi-device admission

The VM size's advertised device count is not topology evidence. Azure's
[GPU VM size catalog][azure-gpu-vm-sizes] and [NC A100 v4 page][azure-nc-a100-v4]
show that device counts belong to exact sizes; the guest
attestor must record every stable device UUID, memory size, PCI bus, NUMA node,
health state, P2P matrix, NVLink/NVSwitch fabric, and RDMA interface. It must
also run a bounded collective and compare the observed rank mapping with the
candidate.

For vLLM:

- host-local tensor parallelism is admissible only inside an attested
  high-bandwidth/P2P group;
- pipeline parallelism is preferred when a model cannot split evenly or the
  devices lack the expected high-bandwidth link, subject to live SLO proof;
- tensor-parallel degree, pipeline-parallel degree, data-parallel degree, rank
  placement, backend, and launcher are explicit evidence fields;
- multi-host operation is a different claim requiring private east-west
  networking, encrypted/control-plane isolation, identical environments, RDMA
  and collective proof, node-loss tests, and a separate admission track; and
- no request may be accepted while one rank is missing or unhealthy.

For Ollama, device selection is runner-managed. `CUDA_VISIBLE_DEVICES`,
`ROCR_VISIBLE_DEVICES`, or `GGML_VK_VISIBLE_DEVICES` is requested intent only.
Admission must independently observe the post-load device set, processor split,
memory high-water marks, and effective context. UUID selection is preferred to
numeric ordinals. A mixed CPU/GPU placement or unexpected device is a refusal
unless the candidate explicitly requested that shape.

The [Azure Container Apps GPU documentation][azure-container-apps-gpu]
currently assigns GPU resources to the first container
and documents no fractional or multi-GPU allocation. Its result must not satisfy
the VM multi-device track.

## Remote workload consumption

The only production endpoint is the Gludd stable logical model profile. The
consumer does not receive the VM address or raw runner URL. Promotion publishes
the candidate generation through the existing gateway dispatcher only after
`RUNNER_READY`.

The proof consumer runs outside the accelerator guest and traverses the same
authenticated, TLS-protected/private-network route used by workloads. The live
proof must include:

1. one buffered and one streaming inference using a nonce and request ID;
2. a receipt tying each request to the logical profile, gateway generation,
   runner generation, exact model revision, and candidate ID;
3. a streaming cancellation that releases its generation lease;
4. timeout, overload/backpressure, and rejected-auth probes;
5. proof that no alternate model, CPU runner, region, or generation served the
   request; and
6. drain proof showing an in-flight request completes on the old generation
   while new requests move to the candidate.

vLLM's `--api-key` does not protect every server path; upstream explicitly
notes an unprotected `/invocations` path. Ollama listens on loopback by default
and must not be treated as an authenticated public service. Both runners remain
behind the gateway/reverse proxy, with direct ingress blocked. Receipts store
only hashes, timings, counts, and identities—not prompts or response content.

## ZDD, rollback, and cleanup

All rollout is replacement-generation rollout:

1. keep the admitted old generation serving;
2. allocate and attest a new leased generation without changing the route;
3. load, warm, and remotely prove the exact candidate;
4. publish only a bounded canary weight;
5. promote only while error, latency, memory, queue, and device-health windows
   remain inside the candidate thresholds;
6. on any breach, atomically restore the old route first, stop new leases to
   the candidate, drain or terminate candidate requests within a bound, and
   retain the failure receipts; and
7. delete only resources bearing the exact lease and ownership labels, then
   prove provider-side absence before reporting `CLEANUP_VERIFIED`.

In-place VM resize, runner replacement under the same generation, broad
resource-group deletion, and best-effort route mutation are prohibited. The
old generation is not drained until the canary observation window passes. The
rollback path is exercised in every live acceptance run, not merely described.

If a provider outage prevents cleanup verification, the result is
`CLEANUP_PENDING`, the cost/expiry alarm remains active, and admission fails.

## Evidence bundle

Each run writes a content-addressed directory:

```text
manifest.json
sources/*.json
phases/*.json
azure/catalog.json
azure/quota.json
azure/allocation.json
guest/devices.json
guest/topology.json
guest/collective.json
sizing/estimate.json
sizing/calibration.json
runner/identity.json
runner/health.json
remote/buffered.json
remote/streaming.json
remote/cancellation.json
rollout/canary.json
rollout/rollback.json
cleanup/absence.json
checksums.sha256
signature.dsse.json
```

`manifest.json` names every expected receipt, its SHA-256 digest, schema
version, phase result, timestamp, candidate ID, lease ID, Gludd commit, and
verifier version. Canonical JSON, hash verification, schema validation,
cross-receipt identity checks, expiry checks, and signature verification must
work offline. Missing, duplicate, expired, unknown, or identity-inconsistent
receipts fail closed.

The live harness emits these stable terminal markers only after offline bundle
verification:

```text
AZURE_ACCELERATOR_ACCEPTANCE_PASS candidate=<id> track=<track> manifest_sha256=<digest>
AZURE_ACCELERATOR_ACCEPTANCE_REFUSED candidate=<id> code=<stable_code>
AZURE_ACCELERATOR_ACCEPTANCE_ROLLED_BACK candidate=<id> code=<stable_code>
AZURE_ACCELERATOR_CLEANUP_VERIFIED candidate=<id> lease=<lease_id>
```

Logs stream a per-phase marker and periodic heartbeat. Long-running allocation,
model loading, calibration, canary, drain, and cleanup operations may not be
silent or redirect their only output to a file.

## Staged verification

| Stage | Environment | Required proof | Failure semantics |
|---|---|---|---|
| 0: schema | Hermetic | JSON schema, canonicalization, source identity, redaction, cross-receipt invariants | hard fail |
| 1: domain | Hermetic | state transitions, sizing arithmetic, TTLs, exact-match selection, rollback decisions | hard fail |
| 2: adapters | Hermetic fakes | recorded ARM responses, quota/capacity errors, guest topology, vLLM/Ollama outputs, gateway leases | hard fail |
| 3: local hardware | Optional, explicitly selected | runner identity, UUID placement, memory/collective probes | `NOT_PROVEN`; never release evidence |
| 4: Azure single GPU | Paid, protected live job | exact allocation through cleanup plus remote proof and rollback | track remains unadmitted |
| 5: Azure multi-GPU | Paid, protected live job | Stage 4 plus topology, ranks, P2P/collective, fault and performance proof | multi-device track remains unadmitted |
| 6: release replay | Hermetic/offline | verify a stored redacted bundle and reproduce the admission decision | hard fail |

Stages 0–2 and 6 run without cloud credentials. Stages 4–5 require an explicit
cost cap, expiry, owner, isolated subscription/resource group, protected
identity, and cleanup alarm. Missing credentials or unavailable capacity yields
`NOT_PROVEN`, never a passing skip.

Tests are written before production code. The release gate must retain at least
85% aggregate coverage and at least 75% per changed executable file, with no
collection errors, warnings, informational update notices, leaked secrets, or
unapproved network access. Live tests never contribute unique lines needed to
meet those coverage floors.

## Admission matrix

| Track | Minimum live evidence | Additional refusal conditions |
|---|---|---|
| Azure VM single-GPU vLLM | Stages 0–4 and 6; pinned source commit, OCI digest, model digests; external buffered/streaming request; rollback and cleanup | unexpected device/model/context, raw ingress reachable, fallback served, missing receipt |
| Azure VM host-local multi-GPU vLLM | single-GPU criteria plus Stage 5 topology/rank/collective/fault proof | partial ranks, unproven P2P group, silent parallelism change, multi-host placement |
| Azure VM Ollama | Stages 0–4 and 6; pinned source/artifact/model; requested and observed device placement; `ollama ps`-equivalent processor evidence | visibility ignored, unexpected CPU split, Vulkan/CUDA backend drift, context drift |
| Remote gateway consumer | admitted runner track plus external network identity, auth rejection, route/generation/no-fallback, cancellation and drain | direct raw endpoint, unbound response identity, content in evidence |
| Azure Container Apps GPU | separate future design and live proof | never inherited from VM proof |
| Google Cloud TPU | separate provider adapter, runtime/model matrix and Google live proof | never inherited from Azure or GPU proof |

An admission decision names exactly one track and exact candidate. There is no
generic “accelerators supported” result.

## Implementation slices

Each slice is one test-first, reviewable commit on a feature branch. Shared
infrastructure and Makefile edits are serialized through one writer.

1. **Acceptance schemas and offline verifier.** Add typed candidate, source,
   phase, and manifest schemas plus malformed/expired/cross-identity fixtures.
   Exit: canonical bundle verifies offline and every mutation fixture fails.
2. **Admission state machine.** Add idempotent transitions, refusal codes,
   resumption TTLs, and rollback decisions. Exit: table-driven tests cover every
   legal and illegal edge without cloud access.
3. **Azure discovery receipts.** Extend the existing read-only Azure strategy
   adapter for Resource SKUs, both quota levels, price/budget, restrictions,
   capacity-unknown, and correlation IDs. Exit: recorded official-shaped
   fixtures distinguish all availability outcomes.
4. **Sizing receipts.** Join exact model artifacts, workload envelope, device
   reserve, and observed calibration without silent substitutions. Exit:
   boundary and overflow tests reproduce every arithmetic decision.
5. **Guest topology attestor.** Produce UUID/PCI/NUMA/link/P2P/RDMA/rank and
   collective receipts. Exit: one-, two-, four-, missing-, reordered-, and
   degraded-device fixtures fail or pass deterministically.
6. **Pinned vLLM adapter.** Verify source/artifact/model identity, parallel
   arguments, health and per-rank observations. Exit: single- and host-local
   multi-GPU fakes prove exact identity; fallback fixtures refuse.
7. **Pinned Ollama observer.** Capture requested UUID visibility, backend,
   `ollama ps`-equivalent placement, context, and memory high water. Exit:
   ignored selection, CPU spill, uneven placement, and backend drift refuse.
8. **Remote gateway probe.** Reuse the existing profile/generation lease path
   for buffered, streaming, cancellation, overload, auth, no-fallback, and drain
   receipts. Exit: a fake raw endpoint cannot satisfy remote proof.
9. **Bundle signing and redaction.** Add canonical hashing, DSSE signing,
   offline verification, retention and secret/content scanners. Exit: tamper,
   truncation, unknown fields, credential, prompt, and response fixtures fail.
10. **Azure live harness and ZDD supervisor.** Add protected single-/multi-GPU
    jobs, phase heartbeats, cost/expiry controls, bounded canary, atomic rollback,
    lease-scoped deletion, and absence verification. Exit: forced failures at
    every post-allocation phase preserve service and clean owned resources.
11. **Release admission receipt.** Replay a redacted live bundle hermetically,
    publish the exact track/candidate decision, update release documentation,
    and preserve the source register. Exit: the normal release gate is green
    and the release claim links the verified manifest digest.

No implementation slice may broaden a release claim merely because the next
live stage is expensive or unavailable.

## Honest TPU boundary

Current [vLLM TPU matrices][tpu-vllm-features] contain untested (`?`) multi-host capabilities, and
TPU generations have generation-specific chip, host, slice, topology, runtime,
and model constraints. A GPU receipt cannot validate any of them. v0.1.2 may
ship schemas and fixtures that keep provider-neutral gateway and model-demand
contracts honest, but it must not advertise TPU execution.

A future TPU track needs its own Google Cloud project/quota/capacity discovery,
TPU VM/slice lifecycle, exact runtime and plugin artifacts, chip/topology and
sharding attestation, model/workload matrix, remote gateway proof, node/slice
failure rollback, cost controls, cleanup proof, and hermetic bundle replay.
Until then the only valid status is `UNADMITTED`.

## Release closeout checklist

- [ ] The exact candidate and every source/artifact/model digest are immutable.
- [ ] Catalog, both quotas, price/budget, allocation and guest identity agree.
- [ ] Static sizing and live calibration cover the production workload envelope.
- [ ] Every requested device, rank, link and collective is independently observed.
- [ ] A separate consumer proves buffered, streaming, cancellation and no fallback.
- [ ] Direct vLLM/Ollama ingress is unreachable; gateway auth rejection is proven.
- [ ] Canary promotion and forced rollback preserve the old serving generation.
- [ ] Cleanup proves absence of every lease-owned resource and retains cost alarms.
- [ ] The evidence bundle verifies offline and its public form contains no secrets/content.
- [ ] Hermetic tests and coverage floors pass without relying on paid live execution.
- [ ] The release claim names one exact admitted track; TPU and untested tracks remain explicit.

Unchecked items are blockers, not optional follow-up work.
