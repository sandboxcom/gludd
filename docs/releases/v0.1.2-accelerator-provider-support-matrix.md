# v0.1.2 accelerator/provider support matrix

Status: implementation-ready design; no accelerator route is admitted by this
document  
Reviewed: 2026-09-28  
Release: v0.1.2  
Design base: `5566d6dcff58c4f6391c9e3b8e3320ed55c73df9`

## Scope and decision

This matrix turns the v0.1.2
[Azure accelerator acceptance design](v0.1.2-azure-accelerator-acceptance-design.md)
into provider-specific implementation inputs. It answers three different
questions without conflating them:

1. Does a provider document the hardware or service?
2. Can a tenant request an exact resource through a documented control plane?
3. Has Gludd admitted an exact provider, device, runner, model, workload, and
   rollout tuple with replayable evidence?

Only the first two questions are upstream facts. Every Gludd execution track in
this document remains disabled or separate until its exact live proof is
verified. Documentation, catalog visibility, quota, a successful allocation,
guest discovery, and one inference response are different evidence phases.

## Provider vocabulary and direct answers

Azure Virtual Machines are Microsoft Azure resources; Amazon EC2 is the Amazon
Web Services virtual-compute product. There is no product named Azure EC2.
Azure VM SKUs, Azure Resource Manager identities, Azure quota, and Azure
capacity receipts cannot be replaced with EC2 instance types, ARNs, AWS quota,
or EC2 launch results. AWS accelerated instances are useful portability inputs,
but they require an independent AWS adapter and admission bundle.

Microsoft's current Azure VM size catalog has GPU and FPGA accelerator
categories but no customer-provisionable NPU VM family. That is a
catalog inference, not a claim that Microsoft owns no NPU hardware. Client NPUs
on Copilot+ PCs are local Windows devices, not Azure tenant resources. Intel
AMX is available in qualifying Azure Intel VMs, but Microsoft documents it as a CPU
instruction-set feature rather than a separate device. Gludd must not discover
AMX as a GPU or NPU lease.

Maia 200 exists and Microsoft documents it as AI infrastructure for Foundry,
Microsoft 365 Copilot, and other managed workloads, with an SDK preview. The
reviewed public Azure VM catalog and Maia announcement provide no
tenant-selectable Maia VM SKU. Therefore v0.1.2 may represent a managed remote
service backed by undisclosed infrastructure, but it cannot promise Maia device
discovery, placement, or direct runner launch.

Yes—Google Cloud TPU is actually provisionable. Google documents TPU VM
creation through its console, API, and command line, and recommends queued
resources when immediate capacity is unavailable. Actual creation still needs
a Google Cloud project, supported zone, quota, and available capacity. Cloud
TPU is not an Azure offering, and its provider lifecycle, runtime, topology,
model matrix, and cleanup proof cannot inherit an Azure GPU result.

Azure inventory is dynamic. The implementation reads the versioned Resource
SKUs API and both relevant quota levels for the requested subscription and
location; it never converts this dated table into a SKU allowlist. Catalog
presence and quota headroom permit only a bounded allocation attempt. Azure
itself documents that allocation can still fail for lack of capacity.

## Device discovery contract

Discovery has provider and guest phases. The provider receipt binds provider,
subscription/project fingerprint, region, zone, resource type, exact SKU,
advertised device count and memory, restrictions, quota, capacity observation,
price, and request correlation identity. The guest receipt independently binds
stable device UUIDs or TPU coordinates, PCI address where applicable, NUMA,
memory, health, driver, firmware, runtime, links, peer-access matrix, RDMA, and
observation time.

Requested counts are intent. Missing, extra, reordered, unhealthy, unknown, or
CPU-fallback devices refuse admission. Azure GPU discovery uses Azure identities
and an Azure guest; EC2 facts cannot fill a missing Azure receipt. AMX is
recorded as an exact CPU capability. FPGA discovery includes XRT, shell,
attested bitstream, and role endpoint. A future TPU adapter records generation,
slice, host/chip coordinates, runtime, and mesh rather than synthesizing PCI
GPU facts.

Hermetic fixtures cover catalog absence, provider restriction, both quota
levels, capacity exhaustion, authentication, throttling, and single, multiple,
reordered, missing, extra, degraded, or CPU-fallback guest observations. Live
discovery remains opt-in, read-only until an explicit leased allocation phase,
and cannot emit an admission marker.

## Multi-device assignment contract

One assignment receipt binds the requested stable device set to every runner
rank and the independently observed post-load placement. It includes tensor,
pipeline, data, and expert parallel degrees; process/rank; device UUID or TPU
coordinate; per-device weights, cache, and peak memory; P2P and fabric facts;
and a bounded collective result.

For vLLM, a model that fits and meets the service objective on one device stays
on one device. Host-local tensor parallelism requires the expected
high-bandwidth peer group. Pipeline parallelism is evaluated for uneven layer
splits or devices without the expected NVLink path. Multi-host operation is a
different claim with private networking, identical environments, node-loss
behavior, RDMA/collective proof, and its own admission track.

For Ollama, `CUDA_VISIBLE_DEVICES`, `ROCR_VISIBLE_DEVICES`, and Vulkan selection
are requested intent, not observed placement. Stable UUIDs are preferred over
numeric ordinals. The implementation records the runner's processor split and
independent per-device telemetry after model load and after inference. An
unexpected CPU split or extra device refuses the candidate.

For TPU, visible device count is insufficient. The future adapter must bind
chip generation, slice and host boundaries, coordinates, topology, process
layout, mesh/sharding, runtime, and collective behavior to the candidate.

## Model right-sizing contract

Right-sizing uses immutable model and workload inputs: repository and revision,
per-file hashes, architecture, parameter count, weight bytes, quantization,
dtype, context, concurrent sequences, batch and token-rate envelope, runner
artifact, and device reserve. It reproduces:

```text
runtime_and_kv = runtime_overhead_bytes
               + kv_bytes_per_token * context_tokens * concurrent_sequences

per_device_required = ceil(weight_bytes / model_parallel_devices)
                    + runtime_and_kv

usable_device_memory = device_memory_bytes
                     * (1000 - reserve_millis) / 1000
```

The estimate only chooses candidates. A bounded calibration at the production
context, concurrency, batch, streaming pattern, and token rate records device
and host high-water marks, latency, throughput, queue depth, and out-of-memory
behavior. Gludd selects the least costly candidate with the fewest devices that
fits and meets the service objective. It never silently changes model,
quantization, dtype, context, concurrency, or runner to create a pass.

## vLLM and Ollama execution contract

The vLLM candidate pins source commit, artifact digest, dependencies, model
revision, backend, launcher, all parallel degrees, context, scheduler settings,
and the exact rank map. Tests cover one device, tensor and pipeline parallel
layouts, uneven splits, missing ranks, collective timeout, wrong device, wrong
model, context drift, and fallback. The server remains behind the Gludd gateway;
runner health is not remote-consumption evidence.

The Ollama candidate pins the binary/container digest, backend, model manifest
and blobs, context and concurrency, requested UUID visibility, and CPU policy.
After load, the observer captures an `ollama ps`-equivalent processor split and
independent memory/utilization for every requested and excluded device. Tests
cover CUDA, ROCm, Vulkan, mixed backends, enumeration reorder, ignored
visibility, stale UUID, CPU spill, unnecessary multi-device placement, restart
drift, and unload/drain.

These are runner-specific contracts. NP FPGA, Maia, AMX, TPU, Inferentia, and
Trainium require compatible runtimes and may not be relabeled as CUDA devices
or assumed to run the same vLLM/Ollama artifact.

## Remote workload consumption contract

The proof client runs outside the accelerator guest and calls a stable Gludd
logical model profile through the production-equivalent authenticated,
TLS-protected route. Direct runner and VM ingress remain blocked. Each buffered
and streaming response binds request ID, candidate, gateway and runner
generation, exact model revision, route, and no-fallback decision without
storing prompt or response content.

The suite exercises buffered inference, streaming inference, cancellation,
timeout, overload/backpressure, rejected authentication, and drain. It proves
that no alternate model, CPU runner, provider, region, or generation served the
request. A guest-local request, raw vLLM URL, or locally exposed Ollama port
cannot satisfy this phase. Ollama binds loopback by default; changing its host
does not by itself add gateway authentication or create remote proof.

Managed endpoints, including any service backed by Maia, use a separate remote
provider contract. They expose service/model/deployment identities rather than
fabricated device UUIDs.

## ZDD and rollback contract

Every change is a replacement-generation rollout:

1. Keep the admitted old generation authoritative.
2. Create a namespaced, leased candidate without changing the route.
3. Discover, size, load, warm, and prove the candidate remotely.
4. Publish only bounded canary weight and observe error, latency, memory, queue,
   and device-health thresholds.
5. Promote only while the whole window remains inside the candidate contract.
6. On any breach, atomically restore the old route first, stop new candidate
   leases, drain or bound termination, and preserve failure receipts.
7. Delete only resources with the exact provider identity, lease, and ownership
   labels; then prove provider-side absence.

In-place Azure VM resize, runner mutation under one generation, destructive
resource-group cleanup, and optimistic fallback are not ZDD. TPU rollback
restores the old gateway route before deleting only the candidate slice. A
managed service rollback restores the previous deployment generation. Cleanup
uncertainty produces `CLEANUP_PENDING`, retains the cost alarm, and blocks
admission.

Tests inject failure after every post-allocation phase, during concurrent
requests, and during cleanup. They prove old-generation availability, route
atomicity, lease accounting, idempotent resume, bounded drain, and exact-target
deletion.

## Evidence and admission status

Evidence uses content-addressed, signed phase receipts for source review,
catalog, quota, capacity, allocation, guest identity, topology, sizing,
calibration, runner identity, remote traffic, canary, rollback, drain, cleanup,
and provider absence. The offline verifier checks schema, canonical hashes,
signature, time/expiry, source version, candidate/lease identity, redaction,
and cross-receipt consistency.

Status semantics are fail-closed:

| Status | Meaning | May the release claim support? |
| --- | --- | --- |
| `DOCUMENTED` | A dated upstream source was reviewed | No |
| `DESIGN_ONLY` | Gludd has an implementation-ready contract but no accepted live bundle | No |
| `OUT_OF_SCOPE` | The route requires an independent design and proof | No |
| `UNADMITTED` | Provider access may exist, but Gludd has not accepted the route | No |
| `SEPARATE_PROVIDER_TRACK` | The surface belongs to another provider adapter | No |
| `NOT_ESTABLISHED` | The named phase has no verified evidence in this artifact | No |
| `ADMITTED` | A future exact track and candidate passed every required phase and offline replay | Only that exact tuple |

Missing credentials, quota, capacity, or hardware yield `NOT_PROVEN` in a live
job, never a passing skip. A provider catalog entry, source review, mock,
structural test, or successful allocation cannot be upgraded to `ADMITTED`.
The structural test for this document validates shape and honesty; it does not
exercise hardware.

## Implementation sequence

Each slice is test-first and produces one reviewable commit:

1. Add typed provider-surface and evidence-status schemas plus mutation
   fixtures for unknown providers, surfaces, and optimistic status coercion.
2. Add Azure Resource SKUs, both quota levels, capacity-result, correlation,
   price, and exact allocation receipts; distinguish absence, restriction,
   quota, capacity, throttle, and authentication.
3. Add guest GPU identity/topology and collective receipts with single, two,
   four, reordered, missing, and degraded-device fixtures.
4. Add immutable model-demand and sizing receipts with overflow, reserve,
   context, concurrency, no-substitution, and calibration reconciliation tests.
5. Add pinned vLLM and Ollama observers, including exact rank/device assignment,
   processor split, memory, context, model identity, and negative fallbacks.
6. Reuse the stable gateway generation/lease path for external buffered,
   streaming, cancellation, overload, authentication, drain, and no-fallback
   receipts.
7. Add replacement-generation canary, atomic rollback, lease-scoped cleanup,
   absence verification, phase heartbeats, expiry, and cost controls.
8. Add provider-specific tracks separately: Container Apps, GCP TPU, AWS, AMX,
   FPGA, or managed Maia-backed services. No track inherits another's result.
9. Replay a redacted live bundle offline before updating any release claim.

Hermetic tests run without cloud credentials. Paid live jobs are explicit,
budgeted, namespaced, least-privileged, observable, and cleanup-bounded. The
project retains at least 85% aggregate coverage and at least 75% in every
changed executable file; live-only branches never carry unique coverage needed
to pass those floors.

Practitioner reports are version-scoped regression inputs, not proof that the
current provider or runner always fails. Closed reports remain valuable because
they preserve real failure shapes.

| [Microsoft Q&A allocation thread][azure-qna-811075] | Opened 2022-04-13; the user reported `AllocationFailed`, with follow-up guidance describing regional physical-capacity limits | Keep catalog, quota, capacity, and allocation as separate receipts; never loop indefinitely or silently change SKU/region. |
| [vLLM #1437][vllm-1437] | Opened 2023-10-20 and closed: the reported four-A10G vLLM 0.2.1.post1 setup timed out in NCCL all-reduce while one GPU started | Require every rank, link, peer matrix, bounded collective, teardown, and exact version in multi-device fixtures. |
| [Ollama #1288][ollama-1288] | Opened 2023-11-27 and closed: the report described lower performance when a model that fit one GPU was spread across several | Prefer the least-device candidate that meets fit and SLO; compare one-device and multi-device calibration. |

The issues do not establish current universal defects. The test corpus records
their version, device, model, and topology assumptions and refuses to
generalize beyond them.

## Release exit criteria

- [ ] One exact provider track and candidate has immutable source, provider,
  guest, runner, model, workload, route, lease, and ownership identities.
- [ ] Discovery proves requested and observed devices with no silent CPU or
  alternate-accelerator fallback.
- [ ] Sizing and bounded calibration prove the production context,
  concurrency, batch, reserve, latency, and throughput envelope.
- [ ] Multi-device claims prove every rank/device, link, collective, placement,
  and per-device high-water mark.
- [ ] A consumer outside the accelerator guest proves authenticated buffered,
  streaming, cancellation, overload, drain, and no fallback through the stable
  gateway.
- [ ] A forced rollback preserves the old generation, and cleanup proves
  absence of only lease-owned resources.
- [ ] The redacted evidence bundle verifies offline with no missing, expired,
  tampered, secret-bearing, or identity-inconsistent receipt.
- [ ] Focused, collection, type, Markdown, coverage, security, and full release
  gates pass at the exact implementation SHA.
- [ ] The release claim names only the admitted exact tuple; NPU, FPGA, Maia,
  TPU, EC2, Container Apps, and multi-host tracks remain explicit unless their
  independent bundles pass.

Unchecked criteria block admission. They are not optional follow-up work.
