## Acceptance state and blocking gaps

### Natural-language plan-only core

The implemented slice is a prototype through non-mutating `plan` and `status`.
It does not provide approval, apply, verification, rollback, HTTP router, CLI,
database lifecycle, or a user-facing end-to-end path. Its catalog entries set
`apply_supported: false`; this is the required safe default.

The commits contain contract, catalog, intent-adapter, planner, collection,
OpenBao-boundary, and adversarial tests. Lightweight collection on the reviewed
heads found 14 adversarial test nodes and 63 collection-module test nodes. Node
discovery proves that those suites collect; it is not passing-test, coverage,
or exact-SHA gate evidence.

The plan-only slice may be integrated dark after all of the following are true:

- focused unit and collection suites pass on the combined integration SHA;
- `config/coverage_configuration.ini` and
  `config/coverage_configuration_boundaries.ini` both prove at least 85%
  aggregate and 75% per measured file;
- documentation labels the slice plan-only everywhere and maps implemented
  behavior to partial NLC12-01, NLC12-02, NLC12-04, NLC12-05, and NLC12-08
  evidence without closing the later lifecycle items;
- the collection has an executable integration or Molecule proof for its
  controller-only delegation, check-mode, OpenBao scope, and zero-mutation
  boundary; and
- no route, role, or module can report a managed host as changed.

Approval/apply/verify/rollback remains a separate future tranche. It must not be
added as a follow-up to this integration without the migration, ownership,
canary, health, idempotence, rollback, and mixed-version proofs specified by
NLC12-06 through NLC12-10.

### Natural-language evaluation

The evaluation tip supplies a 65-instruction corpus, 20 collectable evaluation
test nodes, a hermetic default, an opt-in local gateway seam, exclusive
read-only receipts, a coverage config, a Make target, and a target-contract
entry. It performs no managed-host mutation.

Its current thresholds do not satisfy the feature specification. The feature
spec requires at least 92% exact canonical intent, 97% action-family accuracy,
and 99% ambiguous/unsupported/dangerous abstention recall. The evaluation
artifact currently permits 80% exact arguments, 90% capability/resource
accuracy, and 90% ambiguity/out-of-domain abstention. The stricter feature
thresholds are canonical. The lower values may remain diagnostic floors but
must not set `admission_passed`, qualify a tuple, or appear as release evidence.

Before admission, one reconciliation commit must align code, corpus support,
tests, and both documents to the stricter thresholds; retain 100% unsafe
refusal, 100% fail-closed malformed output, zero unauthorized mutation, and the
lower-confidence-bound rule. Then run the documented hermetic target example,
the target-contract check, focused coverage, and an exact-identity live local
proof. Live evidence is optional for merging dark code but mandatory before any
tuple is enabled for plan generation.

## Forum and practitioner findings retained

The feature documents preserve the user-report evidence that shaped these
boundaries:

- Ansible check-mode and diff reports span from 2014 onward and show missing
  registered values, absent diffs, false `changed` results, host-variable
  surprises, and the diagnostic cost of blanket `no_log`. The plan-only core
  therefore uses catalog-owned probes, direct no-log secret passing, stable
  content-free reason codes, and never treats check mode as convergence proof.
- Long-running Lodash debounce reports pin the difference between a trailing
  quiet period and a fixed-window throttle. CPython executor reports show that
  coroutine cancellation does not terminate a worker thread. The operational
  regressions encode both findings without sleeps.
- Recent Laya and OpenJev user reports show threshold collapse with more
  options, confidently wrong multilingual routing, semantic differences behind
  similar JSON, overload, and very young runtime dependencies. Because there is
  no long-lived production history yet, typed-decision work remains
  provider-neutral, shadow-first, and admission-gated.

These reports are regression inputs, not universal claims. Recheck their state
and upstream release history when a future tranche changes the affected runtime
boundary.
