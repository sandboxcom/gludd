# Terraform / vLLM / llama.cpp / VMware Infrastructure — Design Doc

**Status:** Proposed
**Author:** infra workstream
**Last updated:** 2026-06-28

## Purpose

gludd's compute layer emits all of its Terraform at runtime from Python string
interpolation. There are no reviewable `.tf` artifacts, no VMware/vSphere path,
and a documented HCL-injection surface. This doc records the current state,
enumerates the gaps, evaluates three remediation paths, and recommends one
(Option B — hybrid static modules + dynamic composition) with a phased rollout.

The findings below are the verified starting point — they are not re-litigated:

- The repo has **zero** static `.tf` files. The only `.tf` reference in source
  (`src/general_ludd/infra/deployment.py:116`) is a `main.tf` *path* the runtime
  writes into a tempdir.
- The repo has **zero** VMware/vSphere support.
- All HCL is generated by `src/general_ludd/infra/terraform.py::TerraformGenerator`,
  emitted per `ComputeConfig`, written to a tempdir, and then `terraform
  init/apply/destroy` is shelled out.
- The generator has a documented residual HCL-injection risk from string
  interpolation; tfvars would eliminate it.
- vLLM/llama.cpp **local** serving exists separately via
  `src/general_ludd/infra/local_inference.py::LocalInferenceManager` (spawns
  `vllm serve` or `llama_cpp.server`).
- Planned-but-unimplemented E2E tests for vLLM/llama.cpp are described in
  `docs/e2e_harness/DESIGN_local_cloud_providers_e2e.md`.

## 1. Current state

### 1.1 Dynamic HCL generation

`TerraformGenerator` (`src/general_ludd/infra/terraform.py`) is the single
entry point for "give me a cloud GPU." Given a `ComputeConfig` describing a
provider, region, GPU type/count, container image, and launch script, it:

1. Dispatches to a per-provider method (`_generate_aws`, `_generate_gcp`,
   `_generate_azure`, `_generate_azure_container_app`, `_generate_runpod`,
   `_generate_vast` — plus stubs for LambdaLabs, Modal, Coreweave,
   DigitalOcean, Oracle).
2. Returns an HCL string for a `main.tf`.
3. Writes that string to a per-deployment tempdir.
4. Shells out `terraform init` → `terraform apply` (or `destroy`) in that
   tempdir.

The generator currently supports **10 providers**:

| Provider | Status |
|---|---|
| AWS | implemented |
| GCP | implemented |
| Azure (VM) | implemented |
| Azure Container App | implemented |
| RunPod | implemented |
| Vast.ai | implemented |
| LambdaLabs | stub |
| Modal | stub |
| Coreweave | stub |
| DigitalOcean | stub |
| Oracle | stub |

VMware/vSphere: **absent**.

### 1.2 Local inference

`LocalInferenceManager` (`src/general_ludd/infra/local_inference.py`) provides
the non-Terraform path: it spawns a local `vllm serve` or `llama_cpp.server`
process and exposes a `BASE_URL` for in-process clients. This is what the E2E
harness and dev loops use today; it is orthogonal to the cloud Terraform path
but shares the same `vllm`/`llama_cpp` image matrix.

### 1.3 What does not exist

- No `infra/terraform/` directory.
- No checked-in `.tf` or `.tfvars` files (only `*.tfvars.example` would live
  there under the proposed layout).
- No VMware/vSphere provider, provider info entry, or generator method.
- No `pyvmomi` import (eager or lazy) anywhere in the tree.
- No `.tfstate` / `.tfplan` entries in `.gitignore` — verified by reading the
  file end-to-end (see §8).

## 2. Gaps

| # | Gap | Impact |
|---|---|---|
| G1 | No static, reviewable `.tf` artifacts — every HCL byte is a Python f-string | Code review cannot see the actual HCL that will run; drift between the generator and real provider semantics is invisible until apply-time |
| G2 | No VMware/vSphere provider | Cannot deploy to on-prem/private-cloud GPU capacity; users with vSphere estates have no gludd path |
| G3 | HCL-injection risk in the string-interpolation generator | A `ComputeConfig` field with a stray `"` or `${...}` can produce malformed or malicious HCL. Already documented in the generator's own docstring. |
| G4 | No standalone "deploy a vLLM cluster" / "deploy a llama.cpp server" playbooks, roles, or modules | Each provider re-rolls the vLLM launch script; fixes don't propagate |
| G5 | E2E tests for vLLM/llama.cpp are designed but unimplemented (`docs/e2e_harness/DESIGN_local_cloud_providers_e2e.md` §4.2/§4.3) | Cloud inference paths are unverified end-to-end; regressions land silently |

G1, G3, G4 are the same root cause: the HCL lives in Python strings, not in
files. G2 is additive scope. G5 is test coverage and is orthogonal to which
remediation path is chosen — but it is much cheaper to write once the HCL is
reviewable.

## 3. Options

### Option A — Keep dynamic generation, harden it

Tighten the HCL escaping in `TerraformGenerator` (use `hcl.escape`-style
helpers, never bare f-string substitution). Add round-trip tests that run
`terraform validate` on every generated `main.tf`. Add VMware as a 7th
generator method.

| Pros | Cons |
|---|---|
| Lowest effort — touches only `terraform.py` + tests | Does **not** fix G1 (still no reviewable artifacts) |
| Preserves the single-dispatch flexibility | Injection surface is narrowed, not removed — any new field reintroduces it |
| No migration risk | Operator still cannot `terraform plan` offline or diff stacks in PRs |

### Option B — Hybrid: checked-in static modules + dynamic composition **(recommended)**

Create real `.tf` **modules** under `infra/terraform/modules/` for the
engine-level concerns (`vllm-server`, `llamacpp-server`, `gpu-cost-watchdog`,
`network`). The Python `TerraformGenerator` becomes a **composer**: instead of
emitting inline HCL, it emits a small `main.tf` that contains

```hcl
module "vllm" {
  source = "./modules/vllm-server"
  image  = var.image
  gpus   = var.gpus
  ...
}
```

plus a `terraform.tfvars` file carrying the per-deployment values. The actual
HCL bodies live in version-controlled, reviewable module files.

| Pros | Cons |
|---|---|
| Eliminates G1 (reviewable `.tf`) and G3 (tfvars cannot inject HCL structure) | Medium effort — extract modules from current strings, wire composer, round-trip tests |
| Preserves the dynamic dispatch gludd needs — a `compute_launch` call still works without hand-editing `.tf` | Two sources of truth during the migration window (legacy inline path + new module path); deprecation phase resolves it |
| G4 collapses — one `vllm-server` module serves every provider | Requires `terraform` binary present for `validate` in CI (it already is — `deployment.py` shells out) |
| Small module set stays small as the provider×engine matrix grows | |

### Option C — Full static: one checked-in stack per provider×engine pair

`infra/terraform/<provider>-<engine>/main.tf` for every combination. The
Python layer becomes a stack-selector that copies the right directory and
writes tfvars.

| Pros | Cons |
|---|---|
| Maximally reviewable — every runnable stack is a literal directory | High effort — N×M stacks to maintain |
| No composition logic | Duplicative: the vLLM launch script is copied into every stack; a fix touches N files |
| | Hardest to maintain as the matrix grows (11 providers × 2 engines today = 22 stacks; every new provider doubles) |

---

## 4. Recommendation: Option B (hybrid)

Option B is the only path that resolves **all four** of G1/G3/G4 plus the
reviewability root cause without sacrificing the dynamic dispatch gludd
requires. Concretely:

- **Modules eliminate the HCL-injection surface.** tfvars carry values, not
  structure — a stray `}` in a config field becomes a tfvars parse error, not
  an arbitrary HCL fragment.
- **Composition preserves flexibility.** A `compute_launch` CLI invocation
  still works end-to-end without the operator editing `.tf` — the Python layer
  picks modules and emits tfvars, exactly as today, but the HCL bodies are
  static and reviewed.
- **The module set stays small.** Engine-level concerns (`vllm-server`,
  `llamacpp-server`, `gpu-cost-watchdog`) + one `network` module per provider
  family. The 11-provider × 2-engine matrix collapses to ~6 modules + N thin
  stacks.
- **Option A is a subset of Option B.** Hardening the escaping (A) is still
  worth doing as Phase 0, but stopping there leaves the reviewability gap
  permanently.
- **Option C's reviewability win is illusory** — duplication erodes it the
  first time a fix lands in 22 places and one is missed.

## 5. Proposed directory structure (Option B)

```
infra/
  terraform/
    modules/
      vllm-server/         { main.tf, variables.tf, outputs.tf }
      llamacpp-server/     { main.tf, variables.tf, outputs.tf }
      gpu-cost-watchdog/   { main.tf — cloud-init MAX_COST / TIMEOUT }
      network/             { main.tf — per-provider NSG / firewall }
    stacks/
      aws-vllm/            { main.tf — composes modules + provider config }
      aws-llamacpp/
      gcp-vllm/
      azure-vllm-containerapp/
      runpod-vllm/
      vsphere-vllm/        { NEW — VMware support; hashicorp/vsphere provider }
      vsphere-llamacpp/
    examples/
      aws-vllm.tfvars.example
      vsphere-vllm.tfvars.example
```

- **`modules/`** — pure, provider-agnostic engine logic. A `vllm-server`
  module takes `image`, `gpus`, `model`, `extra_args` and emits the VM +
  cloud-init that runs `vllm serve`.
- **`stacks/`** — one directory per provider×engine. A stack's `main.tf` is
  short: `terraform { required_providers { ... } }`, a `provider "..."` block,
  and one or more `module { source = "../modules/<engine>-server" }` blocks.
  Stacks hold **no** secret material.
- **`examples/`** — `.tfvars.example` files only. Real values come from
  OpenBao via `SecretsManager` at apply time (see §8).

## 6. VMware / vSphere provider addition

Concrete, code-level plan (to be implemented in Phase 2; not in this doc):

1. **Enum** — add `VMWARE = "vmware"` to `ComputeProvider` in
   `src/general_ludd/infra/compute.py`.
2. **Provider info** — add a `ProviderInfo` entry in
   `src/general_ludd/infra/providers.py` with:
   - `terraform_provider: "hashicorp/vsphere"`
   - `auth_env`: `VSPHERE_USER`, `VSPHERE_PASSWORD`, `VSPHERE_SERVER`
   - `auth_source`: resolved through `SecretsManager` / OpenBao (never raw env)
3. **Generator method** — add `_generate_vsphere(self, config)` to
   `TerraformGenerator`, modeled on `_generate_azure` (closest existing
   shape: VM + `custom_data` cloud-init + managed disk). Under Option B this
   method emits a `module { source = "../modules/vllm-server" }` block + a
   `provider "vsphere"` block; it does **not** inline the VM resource.
4. **Python client** — lazy-import `pyvmomi` under a `[compute]` extra. Do
   **not** add as a hard dependency. Import inside the method body, not at
   module top.
5. **Stack** — add `infra/terraform/stacks/vsphere-vllm/` (and
   `vsphere-llamacpp/` once the llama.cpp module lands).
6. **Examples** — add `examples/vsphere-vllm.tfvars.example` with placeholder
   `datacenter`, `cluster`, `datastore`, `network` keys.

## 7. Phased rollout

| Phase | Scope | Exit criteria |
|---|---|---|
| **Phase 0** (optional, immediate) | Tighten HCL escaping in current generator; add `terraform validate` round-trip tests on all existing provider methods | `tests/unit/test_terraform_validate.py` green for all 6 implemented providers; documented escape helper |
| **Phase 1** | Extract `vllm-server` + `llamacpp-server` modules from current string-interpolated HCL. Rewrite `TerraformGenerator` to emit `module { source = "...modules/<engine>" }` + tfvars instead of inline resources. | `tests/unit/test_terraform_modules.py` green: every supported provider×engine pair passes `terraform fmt -check` and `terraform validate`. Existing cloud-deploy call sites unchanged from the caller's perspective. |
| **Phase 2** | VMware/vSphere end-to-end (§6): enum + provider info + generator method + `vsphere-vllm` stack + `tests/unit/test_vsphere_provider.py`. | `make test-unit` green; `terraform validate` on `stacks/vsphere-vllm/`; vSphere creds flow documented as OpenBao paths, not env vars. |
| **Phase 3** | Implement E2E tests from `docs/e2e_harness/DESIGN_local_cloud_providers_e2e.md` §4.2 (vLLM) and §4.3 (llama.cpp), gated on `VLLM_BASE_URL` / `VLLM_E2E_SPAWN` env vars so they skip in CI by default. | `tests/e2e/providers/test_vllm_e2e.py` passes when env vars are set, skips cleanly otherwise. |
| **Phase 4** | Deprecate the legacy string-interpolation paths once every provider is module-backed. Remove the inline HCL templates. | No `_generate_*` method emits inline resource HCL; all emit module blocks. `grep -R 'resource "' src/general_ludd/infra/terraform.py` returns zero hits. |

Phases are independently mergeable. Phase 0 can land before Phase 1 if the
escaping hardening is wanted as a stopgap.

## 8. Security considerations

- **VMware credentials via OpenBao, never raw env.** The `SecretsManager`
  pattern already used for cloud keys applies directly: `VSPHERE_USER` /
  `VSPHERE_PASSWORD` / `VSPHERE_SERVER` are fetched at apply time from the
  existing secrets backend and written into the ephemeral tfvars in the
  tempdir, which is destroyed after `terraform apply`.
- **tfvars discipline.** Real values never enter `infra/terraform/`. The
  `examples/*.tfvars.example` files contain placeholders only. A
  pre-commit check (detect-secrets is already in the tree) should be extended
  to scan `infra/terraform/**/*.tfvars` for non-example files.
- **`.tfstate` / `.tfplan` gitignore coverage is currently MISSING.** Verified
  by reading `.gitignore` end-to-end: there are no entries for `*.tfstate`,
  `*.tfstate.*`, `*.tfplan`, `.terraform/`, or `*.tfvars` (the last is
  intentional for `*.tfvars.example`, but `*.tfvars` real files must be
  ignored). **Phase 1 must add these entries** before any stack is checked
  in. This is a blocker for committing the first `.tf`.
- **HCL-injection removal.** Under Option B the injection surface documented
  in the current generator goes away structurally — tfvars are values, not
  HCL. The escape helper from Phase 0 becomes defense-in-depth, not the
  primary control.
- **Provider plugin pinning.** Each stack's `terraform { required_providers
  { ... } }` block pins provider versions (e.g. `hashicorp/vsphere = "~>
  2.8"`). No floating `>=` ranges.

## 9. Testing strategy

| Test file | Scope | Phase |
|---|---|---|
| `tests/unit/test_terraform_validate.py` | Round-trip: `TerraformGenerator` output for every implemented provider×engine passes `terraform fmt -check` + `terraform validate`. Skips if `terraform` binary absent. | 0 / 1 |
| `tests/unit/test_terraform_modules.py` | Every module under `infra/terraform/modules/` and every stack under `infra/terraform/stacks/` passes `terraform fmt -check` + `terraform validate`. Asserts that stacks reference modules by `source`, not inline resources. | 1 |
| `tests/unit/test_vsphere_provider.py` | `ComputeProvider.VMWARE` exists; `providers.py` has the vsphere `ProviderInfo` with the three env vars; `_generate_vsphere` produces HCL that references `../modules/vllm-server`; `pyvmomi` is lazily imported (assert `pyvmomi` not importable at module top-level). | 2 |
| `tests/unit/test_terraform_escape.py` | Phase 0 escape helper: config fields containing `"`, `${`, `\n`, `}` produce valid tfvars values (quoted, escaped) and never produce valid HCL structure. | 0 |
| `tests/e2e/providers/test_vllm_e2e.py` | Real vLLM spin-up gated on `VLLM_BASE_URL` + `VLLM_E2E_SPAWN`. Validates `/v1/models`, `/v1/completions` round-trip. Skips if env vars unset. | 3 |
| `tests/e2e/providers/test_llamacpp_e2e.py` | Same shape for `llama_cpp.server`. | 3 |

All unit tests must be hermetic (no real cloud calls). `terraform validate` is
the boundary: it exercises real HCL parsing without provisioning. E2E tests
are env-gated and never run in default CI.

## 10. Open questions (to resolve before Phase 1 merges)

1. **tfvars templating engine** — plain `str.format` with a strict allowlist,
   or adopt `python-hcl2` for writing? Leaning toward the allowlist to avoid
   a new dep.
2. **State backend** — local `.tfstate` in tempdir (current behavior) vs.
   remote state in OpenBao's KV store. Remote state is safer for long-lived
   clusters; local is simpler for ephemeral ones. Proposal: remote for any
   deployment with `MAX_COST > $X`, local otherwise.
3. **Provider plugin cache** — share `~/.terraform.d/plugin-cache` across
   tempdir runs to avoid re-downloading the vsphere plugin (~80 MB) on every
   `init`. Low priority.

These do not block the recommendation; they are Phase 1 design details.

## Appendix A — Why not "just write a YAML schema and generate HCL from it"

A YAML/DSL-to-HCL generator (e.g. `cdktf`, or a custom schema) would move the
string interpolation from Python to another templating layer without making
the HCL reviewable in `.tf` form. Option B's modules already solve the
reviewability problem in the language Terraform natively speaks. Adopting a
DSL would add a translation step and a dependency for no incremental benefit
over checked-in modules + tfvars composition.
