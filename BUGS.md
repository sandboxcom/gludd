### 2026-08-16 — (resolved) Infinite game-gen rejection loop: include-var shadowed the retry counter

- **What happened**: The local_game_gen molecule scenario looped forever — 16+ generation attempts with `max_attempts=3`. Every retry re-ran the whole generate→verify→reject cycle because the `when: _attempt | int < max_attempts | int` guard on the self-include always saw the stale value 1.
- **Root cause**: `main.yml` included `generate_and_verify.yml` with `vars: {_attempt: 1}` — an INCLUDE VAR, not a host fact. Include vars shadow host facts inside the included file, so the rescue's `set_fact: _attempt: "{{ _attempt | int + 1 }}"` wrote the incremented FACT while every subsequent read of `_attempt` inside the file still resolved through the shadowing include var (always 1). The guard could never see the increment → unbounded recursion.
- **Fix applied** (`de25ad544`, CI-validated round-13 molecule green): the counter starts via `set_fact` as a host fact; the include carries no vars. Regression pin `test_attempt_counter_starts_at_one` asserts set_fact-start + no-vars-on-include. Local molecule run: exactly 3 attempts, artifact removed, `REJECTED ... after 3 attempt(s)` surfaced, verify rejection path green.
- **Lesson**: Never pass a mutable counter into `include_tasks` as an include var when the included file self-recurses and increments it via `set_fact`. Include vars shadow facts; facts propagate. Counters must be facts from the start.

### 2026-07-27 — (resolved) CI RED: pkg_resources (setuptools) import crash in Python 3.14 binary smoke test

- **What**: CI run 30310764100 on HEAD `0d080ca5` failed with `conclusion=failure`. The Python 3.14 binary smoke test crashed with an import error: `ModuleNotFoundError: No module named 'pkg_resources'`. Python 3.14 removed `pkg_resources` (deprecated since setuptools 67.5.0, replaced by `importlib.resources` and `importlib.metadata`), but the binary was still importing a shared library or ansible plugin that referenced the deprecated module.
- **Why guardrail failed**: The CI binary smoke test (`./dist/gludd --version`) was added in the macOS binary crash fix but didn't anticipate that Python 3.14 would remove `pkg_resources` entirely. The binary built correctly on Python 3.12 but failed on 3.14 because the deprecated module was physically absent, not just deprecated.
- **Root cause**: The gludd binary imports ansible modules that transitively depend on `pkg_resources`. When PyInstaller bundles the binary, it follows import chains into code paths that try to `import pkg_resources`. On Python 3.14, this module doesn't exist, so the import crashes — even if the application code never calls it directly. The fix was preemptive: force-assign an empty `pkg_resources` namespace before the import chain fires, satisfying the import without loading the nonexistent module.
- **Fix applied**: (1) Added a `pkg_resources` force-assignment stub (a synthetic `pkg_resources` module to satisfy import chains) so the binary smoke test passes on Python 3.14. (2) Updated `store.py` to use an `importlib` pattern for filesystem imports to avoid E402 lint violations. (3) Fresh CI triggered (run 30312772822). Commits: `19f937e8`.
- **Lesson**: A `ModuleNotFoundError` for a deprecated module that an application doesn't directly use is an import-chain problem: PyInstaller follows transitive imports, and if any code path references a module that doesn't exist on the target Python version, the binary crashes at import time — before any application code runs. Preemptive stubs (synthetic empty modules) for known-removed dependencies prevent this class of crash. CI must test binaries on the target Python version (3.14), not just the build version (3.12).

### 2026-07-27 — (resolved) Enforcement-plugin pressure-release deadlock: agent deadlocks when dispatches fail while streak counter blocks inline recovery reads/edits

- **What**: When task dispatches failed (e.g., model temporarily unavailable), enforcement plugins' streak counters incremented on the dispatch attempts but the failed dispatches did NOT reset the counters. After 4+ consecutive failed dispatches, ALL tool calls (including reads and edits needed to diagnose and fix the problem) were blocked by the streak counter — but the agent couldn't dispatch subagents to reset the counter because dispatches themselves were the failing operation. This created a pressure-release deadlock where recovery was structurally impossible.
- **Why guardrail failed**: Enforcement plugins (enforce-floor.ts, enforce-delegate.ts, enforce-multitask.ts, enforce-stop.ts) counted dispatch ATTEMPTS but only reset streak counters on SUCCESSFUL dispatches. A failed dispatch (timeout, 429, model unavailable) looked identical to a non-dispatch call from the counter's perspective — it incremented the streak. When 4+ consecutive dispatches all failed in a row, the counter hit its threshold and the hard-denial path activated, blocking reads/edits that could have fixed the underlying issue (e.g., switching to a fallback model, adjusting the dispatch config). The agent was in a deadlock: it couldn't dispatch (the operation was failing), and it couldn't read/edit to fix the dispatch path (reads were blocked by the streak counter).
- **Root cause**: The streak counters had no "failed dispatch" classification — they only tracked "dispatch" vs "non-dispatch", with no allowance for dispatch ATTEMPTS that fail for transient reasons. A fleet of failed dispatches saturated the counters and triggered the hard block, while the failure condition that needed fixing was in the dispatch path itself. The pressure-release mechanism (MAXBLOCK counter, default 5) was reachable but the interim period (5 consecutive blocked calls) was a deadlock window.
- **Fix applied**: (1) Added failed-dispatch detection to all enforcement plugins: when a dispatch returns a transient-failure status (timeout, 429, 503, no model available), the streak counter is RESET instead of incremented, preventing failure saturation. (2) Added a degraded-mode pressure-release path in enforce-floor.ts, enforce-delegate.ts, enforce-multitask.ts, and enforce-stop.ts that automatically lowers enforcement thresholds after N (default 3) consecutive failed dispatches. (3) Added shared.ts utility functions for failed-dispatch classification, degraded-mode state management, and pressure-release threshold calculation. (4) New test files: `test_multitask_pressure_release.py` (verifies pressure-release path + failed-dispatch detection) and `test_enforce_stop_subagent_deficit.py` (verifies stop hook doesn't fire on transient dispatch failures). (5) BUGS.md entry documented. Commits: `63d971bf`.
- **Lesson**: Enforcement counters that classify all failed dispatches as "streak-incrementing" are structurally self-locking when the failure IS the dispatch path. Failed dispatches must RESET the streak counter, not increment it — a blocked dispatch is not a "failure to delegate," it's a "dispatch attempted but unavailable." The pressure-release path (degraded-mode threshold lowering) is the safety valve for the case where failures persist: after N consecutive failures, let reads/edits through even at the cost of floor compliance, because the only way to fix the dispatch path is to read/edit config or code.

  9. **P7: MAXBLOCK escape.** Added bounded MAXBLOCK counter (default 5) to enforce-floor.ts and enforce-delegate.ts: after N consecutive denials without a dispatch, the block is temporarily released with a loud warning. Prevents permanent wedging.
  10. **P8: Polarity trap.** Added assertion that `GLUDD_FLOOR_ENFORCE=0` is an explicit opt-out, not the default. The env var is now treated as a boolean: absent = enforce (default ON), `"0"` = disable, `"1"` = enforce explicitly. A missing env var no longer silently defaults to advisory mode.
